# Review item 4: current boundaries and narrow integration point

- `extension_sources::select_sources` already enumerates built-in JSON plus applicable providers into deterministic `SourceDescriptor` order and rejects record-ID collisions. `CustomSourceSnapshot` pins that table, its source generation and the participating selection/decoder semantics. `query_frontend` uses it; ordinary query paths do not.
- `Repository::collection` in `source_records.rs` rejects a collection containing custom records. `json_query`, `text_query`, `views`, `get_record` and the native picker reconstruct `{id}.json` and therefore cannot materialize provider records. This rejection also makes ordinary refresh and warm/build APIs fail or bypass the native picker.
- `JsonFilter` and view projection consume `serde_json::Value`; `TextMatcher` traverses that value and already applies schema-bound Markdown/HTML/XML rules. The selected-index builders consume borrowed `DecodedRecord` values directly. Public `Record` owns a JSON-compatible `data` tree, so returned custom pages need materialization, while default JSON queries keep their existing concrete parser and indexes.
- `build_selected_indexes` shares one provider read/decode among requested representation and derived postings, but only explicit calls use it. Selected posting snapshot APIs validate descriptors and revisions but have no normal `.objekte/.cache` lifecycle. `refresh` currently returns early when a custom source is present, leaving the native picker unreconciled.

The integration boundary is a per-collection selected-record route, entered only when its pinned inventory contains a custom source. It uses `SourceDescriptor` for reads and page materialization, reuses compiled native filters/scanners and selected postings, and publishes inventory/index changes through the existing repository refresh/cache generation. JSON-only collections continue through the concrete picker and fused projection path.
