# Selected representation snapshot stage control

## Source and inputs

Starting revision: `6f1a86bef9` on `library-extensions-stage2-wip`; implementation commit: `8fdb267dbe`. The stage adds an explicit, versioned selected-representation snapshot. Its filter uses the existing portable bigram codec; a companion manifest persists the registered descriptors, bound representation identity, selected-source revision fingerprint and filter-file SHA-256. The codec uses synthetic `.json` slot labels because its portable file manifest expects JSON filenames. The engine compares those labels with the actual provider record IDs and validates the companion before publishing the filter. Default JSON picker snapshots and startup remain on their existing path.

The real-corpus control used `RAYON_NUM_THREADS=16 taskset -c 0-15 candidate-bin/frontend_index_compare examples/musenalm 7` in five separate processes. Each process built, saved and restored the selected `objekte:visible-markdown` posting for `contents.annotation`, then compared all complete ordered IDs, count and truncation with an exact scan. The same pinned Musenalm source paths and metadata were used: 148,486 records overall, source/content/stat SHA-256 `90e36ad63dcb6386e9521c583fdcd36451fd3d6182187dced542fb8292f730ce`; the selected `contents` collection had 133,948 records. The workload and manifest are under this directory. Builds and restores used normal release code, 16 Rayon threads and CPU affinity 0–15; filesystem caches were warm and not evicted. Repository opening is outside the reported build/save/restore timings.

The default JSON control paired the prior-stage and candidate release `json-query-mix` binaries through `run_paired_json_extension.py`: 50 loaded cases, ASCII bigrams, 0/64 MiB cache budgets, three alternating process pairs and seven rounds per process. The pinned 50-case workload SHA-256 was `d7e6967dc1250cf28c054027c72fba8452f5ccd4e8fe3eea9653423fa135e7d7`. `manifest.json` and `json-50/manifest.json` contain exact binary hashes, commands and input identities; `frontend-01.json` through `frontend-05.json` and `json-50/` retain raw samples, exits and stderr. Executables are preserved under ignored `candidate-bin/`, outside commits.

## Results

The 8,122,681-byte filter snapshot restored in a median 424.355 ms (416.482–430.230 ms) across five processes, with zero source reads and parses. Fresh index build took median 3,725.866 ms (3,711.404–3,748.348 ms); snapshot save took median 418.800 ms (416.016–422.286 ms). Restore includes current source-descriptor enumeration, payload hashing and decoding; build additionally reads, parses and renders all selected sources. These are separate operations rather than equal-work timing comparisons.

All five restored complete ordered 284-ID results matched the scan. Across 35 measured rounds per path, exact scan median was 3,145.270 ms (3,124.853–3,310.729 ms), with 133,949 reads and parses per query. Indexed median was 9.537 ms (9.067–9.698 ms), with 326 reads and parses per query. The restored query was also compared with the complete scan before each process exited.

All 50 default JSON case signatures and per-case scan/read/parse counts matched at both budgets in every pair. The median case delta (candidate minus prior stage) was -0.024 ms at cache 0 and -0.033 ms at cache 64. The largest positive median of paired medians was +0.204 ms at cache 0 (case 2, 118.092 ms reference) and +0.120 ms at cache 64 (case 45, 32.236 ms reference). No case showed a material repeatable slowdown in this targeted control; `json-50/summary.json` has every per-case delta.

An exploratory early size precheck for the explicit snapshot path was then compiled and measured. Its five `frontend-final-*.json` runs retained correct results and median restore 422.453 ms, but `json-50-final/` showed repeatable default JSON deltas up to +0.828 ms at cache 0 and +0.941 ms at cache 64, concentrated in cases 40, 41 and 45 with unchanged work. The precheck was reverted before committing production code. Both raw sets are preserved; the accepted measurements and binary hashes are the unsuffixed `frontend-*.json` and `json-50/` controls. An oversized user-supplied snapshot path is hashed before the portable codec rejects its size; an earlier cap check remains an open hardening item because the measured variant regressed default queries.

## Correctness and limits

The external consumer test verifies exact restored results, zero source reads/parses during restore, rejection of a damaged payload, a changed decoder semantic version, a changed manifest version, and a changed source revision. The engine publishes only after complete validation. Workspace tests, Clippy with warnings denied, and the combined `index-timings,allocation-profile` benchmark feature tests passed. Changed Rust files pass rustfmt and `git diff --check`. The whole-workspace spacing check still reports the same seven pre-existing hunks in five untouched files; logs are saved under `validation/`.

Persistence is explicit: callers choose a snapshot path and rebuild on `Ok(false)` from restore. Provider sources remain outside the legacy JSON picker and its snapshots; the final Phase 0 matrix, large-corpus source oracles and remaining module migration are open. This stage alone does not establish final acceptance.
