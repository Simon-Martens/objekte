# Paused library extension implementation: build-profile gate

Reference production revision: `266d9a0fb071838be8f757671599872a7036a054` (clean at Phase 0). The attempted candidate is the uncommitted production patch saved in `tracked-production.patch` plus `new-files/`; their hashes are in `manifest.json`. All production files, `Cargo.toml`, and `Cargo.lock` were restored to the reference revision after this report. Benchmark-only harness changes and the Phase 0 raw baseline remain in the working tree.

Generated reference/candidate executables and index snapshots remain available locally and are ignored by Git. The tracked manifests, checksums, source patch, commands and raw measurements describe how to rebuild them.

## What the paused patch did

The patch added statically linked descriptors and registration contracts for sources, formats, representations, typed extractors, operators and frontends. It made registered text representations/operators executable through `Repository::search_text_with` and `search_text_stream_with`, while specializing the default text path at compile time. A separate consumer crate registered a prefix scanner and independent trimmed representation, exercised the current Markdown/HTML/XML renderers through public registration, and checked scan-only versus raw-bigram candidate execution. It retained custom schema annotations only for registered dependencies, without changing the default `Schema` layout. Existing workspace tests and targeted Clippy passed; extension tests covered markup parity, Unicode folding, refresh, schema reload, streaming and callback cancellation.

Source-provider, format-decoder, typed-extractor and frontend registrations were not yet wired into repository execution. The paused patch is not a complete library extension implementation and should not be applied as a finished feature.

## Gate evidence

The required instrumented Musenalm FTS build profile showed a repeatable slower candidate. The initial five alternating 16-thread runs in `stage2-text/index-build-musenalm-fts4/` had median build times of 2,709 ms reference and 3,158 ms candidate (+16.5%). After moving the schema annotation tree out of `Collection` to restore its default layout, five fixed P-core runs in `stage2-text/index-build-no-schema-layout/` still had medians of 2,752 ms reference and 3,081 ms candidate (+12.0%). Earlier fixed-core diagnostics were less stable, with some candidate runs near parity; all raw runs are retained. The index profile's document counts, compressed index bytes, base/secondary snapshot sizes and allocation counts remained equivalent. The candidate's source-read, parse and projection stages took more wall/CPU time without more instructions or source work.

The separate normal release CLI control in `stage2-text/normal-release-control/` did not reproduce the slowdown: five alternating reindexes had medians of 3,340 ms reference and 3,296 ms candidate; fresh-process base-plus-secondary restore/query was 554 ms versus 555 ms. Ordered IDs, count 2,908, truncation and snapshot load counters matched. The FTS query control in `stage2-text/final-fts/` matched all 30 signatures with cache off and on and performed the same scans/parses. Its median case relative deltas were -2.93% cache off and +2.33% cache on; these runs preceded the final schema-annotation storage adjustment. The full JSON cache on/off comparison at the earlier candidate state also matched all 152 signatures, but had noisy per-case timings. Allocation rows had largely equal per-query counts. The initial stream fixture's implicit timestamps were corrected; the deterministic reference/candidate replay in `stream-fixture-v2/` has exact ordered-ID and work parity.

`../corpora-after-candidate.json` exactly matches the Phase 0 corpus fingerprint, including source metadata, after all candidate measurements. The restored production checkout passed `cargo test --locked --workspace --all-targets` and workspace Clippy. Its spacing check still reports only the two pre-existing differences recorded at Gate 0.

Three-code-state diagnostics are in `stage2-text/index-build-schema-only/`, `index-build-discovery-variant/`, and `index-build-registry-variant/`. A schema-only or schema-plus-discovery build of the unchanged reference stayed near the reference profile. Adding registry/repository code moved some runs upward; adding the text execution patch produced the slowest instrumented runs. `perf stat` samples under the same P-core affinity showed roughly 76.5 billion instructions for both binaries, while candidate cycles and IPC varied substantially. This does not establish a deterministic algorithmic cause. It also does not resolve the observed instrumented slowdown.

## Decision and resumption

The user's gate rejects a reproducible slowdown and treats unresolved variance as open. The candidate was therefore archived and production code restored. Phases 3–6 and the final performance matrix were not attempted. To resume, apply the archived patch in a disposable checkout, retain the separate reference binaries and corpora, isolate the instrumented build difference, and rerun the full gate before adding more extension categories. Do not report the extension library or no-regression acceptance as complete from these measurements.
