# Direct Rust, Node objects, Rust SQLite cache, and Rust qj rerun

Rerun on 28 October 2026 at commit `af1569bc7f`, using an AMD Ryzen 7 5700G, Node.js 26.3.0, Rust 1.96.0, qj 0.3.0, and rusqlite 0.41.0 with bundled SQLite. Release binaries were built with `cargo build --offline --locked --release -p objekte-bench --features sqlite-bench --bin shared-query-compare --bin array-compare` and `cargo build --offline --locked --release -p objekte-bench --bin musenalm_rust_full --bin musenalm_rust_projected`. Source files and generated benchmark inputs were on btrfs under this repository; the OS file cache was uncontrolled. The measured time excludes process startup. No authoritative example files were changed.

These are fresh measurements on a different CPU from the earlier tables in [RESULTS.md](RESULTS.md) and [Performance.md](../../Performance.md). They are not speedup measurements against those tables.

## Shared scalar workload

The [shared runner](src/bin/shared_query_compare.rs) used the same four operations and checked complete result equality: integer range count, range filter plus numeric/ID sort and first 50 rows, grouping by integer field, and ASCII case-insensitive text count. Node retained full parsed objects from original JSON files. The two **non-indexed direct Rust** modes also read original files: `rust-source` retains complete `serde_json::Value` trees, while `rust-projected-source` chooses the numeric and text fields by runtime arguments and retains only those fields plus IDs. Embedded qj loaded a previously prepared NDJSON snapshot. Rust SQLite imported original JSON files into a disposable disk JSONB database; the indexed row uses an expression index on the numeric field. Each value below is the median of three fresh processes, each with one warm-up and three timed query executions. Loads include parsing or database import. The index and source scan are separate.

The [full-data Rust runner](src/bin/musenalm_rust_full.rs) and [Node runner](src/bin/musenalm_node_full.mjs) loaded all **148,486 JSON files** from the seven `data` directories and executed matching count, filter/sort/page, nested-array facet, text-search, ID-link, and contributor-join queries. ## Interpretation and limits

For these particular hand-written warm queries, Node objects were fast after full loading. Full generic `serde_json::Value` trees in Rust used substantially more memory and were slower on the large collections. Runtime-selected Rust projections were fast and small, but this runner has only four fixed scalar query shapes. The typed full-data projection has a Musenalm-specific field list. Indexed SQLite was much faster for matching repeated pages, while its build, index, and source-reconciliation costs must be included when deciding whether to cache a view. qj remained a working embedded reference but required a generated snapshot and more memory here. The scalar workload covers only top-level integer and text fields; the nested suites are Musenalm-specific. None implements the MVP's collection-neutral declarative `list`/`view` API, external-edit invalidation, schema validation, raw grep, or cleaned search. The [MVP decision gate](../../MVP.md#general-benchmark-and-performance-decision-gate) remains open.

Commands are in [README.md](README.md). Raw scalar and full-data JSONL output plus complex-suite text output are retained locally in `target/bench-rerun-2026-10-28/` (ignored by Git); the temporary SQLite databases were removed after measurement.
