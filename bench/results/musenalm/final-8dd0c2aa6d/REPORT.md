## Registration and implementation scope

The fixture declares seven JSON/filename-identity collections with 148,486
independently addressable records: `agents` 4,010, `contents` 133,948,
`entries` 4,928, `items` 4,180, `pages` 8, `places` 210, and `series` 1,202.
The integration layer registers a standalone JSON reader/scanner, logical
value and nested-string extraction, schema-declared typed B-tree lookups,
record-level raw bigrams, ICU `de` sorting columns for the fields listed in
`run-manifest.json`, and one custom folded binding. No unused XML/HTML/Markdown
reader was registered. Metadata is derived from the file/record inventories.
The generic core uses versioned, checksummed snapshots and record-slot indexes;
the archived `old/` implementation was inspected for behavior but no archived
crate is linked.

The `agents.name:folded@1` registration uses Unicode case folding for both
query and record names, a separate folded bigram candidate path, and matching
scanner verification. In an alternating five-pair build experiment with
snapshots disabled, adding that binding increased full ASCII build time by
19.2–54.2 ms per pair (median 29.7 ms) and process resident memory by
0.60–0.84 MiB per pair. Its own estimated index heap is 376,302 bytes
(0.359 MiB). [The experiment source](custom-binding-measure.rs),
[raw samples](custom-binding-samples.jsonl), and
[build log](custom-binding-build.log) are saved. These are measured marginal
costs in this fixture, with process noise; the total build and index memory
figures above include the binding.

FTS is a literal substring input separate from FILTER. FILTER has typed
comparison/contains operators, Boolean precedence, array quantifiers,
modifiers, and reserved metadata paths; declared dates, datetimes, and Unix
seconds remain distinct from string-shaped values. COUNT covers all matches;
the page can return locators, original record bytes, or logical values with
matched-field evidence. The [implementation guide](../../../../docs/search-core.md)
documents grammar, type behavior, indexes, caches, sorting, inventory,
snapshots, and the [future complete-file update boundary](../../../../docs/future-whole-file-replacement.md).

## Reproduce and limits

```bash
cargo test --workspace --all-targets
cargo run --release --example accept_musenalm -- --alphabet ascii
cargo run --release --example accept_musenalm -- --alphabet unicode
cargo run --release --example bench_musenalm -- \
  --profiles ascii-off,ascii-warm,unicode-off,unicode-warm \
  --verified-cache-bytes 67108864 --repetitions 5 \
  --result-dir /tmp/musenalm-final-reproduction
```

Use an unused result directory because the runner creates the raw sample file
exclusively. The saved `run-manifest.json` records exact arguments, fingerprints,
registrations, environment, and the measured revision. The build repeats are
independent Q031-only runs; their manifests give exact commands. There is no
historical warm-cache or restore measurement at the initial C16 baseline
revision; the later C24 baseline is used for restoration. There is no
additional historical query suite. Source freshness checks rely on path,
size, and modified time; same-size edits with a restored timestamp cannot be
detected. Runtime updates, watchers, and partial repository rebuilds remain
deferred. The project branch's pushed commits and checks are mapped in the
[progress ledger](https://github.com/Simon-Martens/objekte/blob/0edd50292a/docs/core-implementation-progress.md).
