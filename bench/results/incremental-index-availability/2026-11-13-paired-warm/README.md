# Plan 1 seven-pair warm construction comparison

`run_pairs.py` alternated baseline and candidate order for seven pairs, launching each measurement in a fresh process. Both binaries read the same absolute Musenalm root (`/home/simon/source/objekte/examples/musenalm`), with ASCII bigrams, 32 workers, configured schemas, inference disabled, profiling, snapshot writing and five query probes. The baseline binary was built from `7a6b96684e1fbb849eab7cc20185b942159ed189`; the candidate binary was built from integrated Plan 1 commit `bad06b4007476c7f861fe9f1090e9d7be744218e`. `runs.json` embeds all 14 benchmark samples, commands and manifests. Corpus and schema fingerprints agree across runs. The large snapshot payload files were deleted after their byte counts were captured.

Quartiles in `summary.json` use Python's inclusive fourths. Median full build fell from 967.277 to 896.591 ms (7.31% faster). Median fresh-process build high-water RSS rose from 535.683 to 573.788 MB (7.11%); median post-build RSS rose 8.65%. The comparable index-family estimate rose from 69.663 to 69.966 MB (0.43%). Both modes parsed 148,486 records; candidate construction made exactly 148,486 source reads totaling 193,297,230 bytes. Candidate median first searchable batch and first result were 334.747 and 334.904 ms. Snapshot bytes were 129,139,458 baseline and 178,287,528 candidate; the larger persisted lifecycle representation is reported separately from the agreed live-index and peak-RSS gates.

The comparison used warm filesystem cache. It does not measure cold storage latency or a concurrent foreground query. Those are separate task checks.
