# Sorting the Musenalm 50-query workload — 2026-11-01

Release build at core commit `2482bfa177` on an Intel Core i9-13900K (32 logical CPUs, 30 GiB RAM). The benchmark keeps one repository handle open, warms all seven indexes, runs every case once without timing, then measures three rounds in alternating case and baseline/sort order. Each request counts matches up to the repository cap of 10,000 and returns 25 records. The untimed pass and every timed round check equal capped counts and stable first pages. Source JSON and schemas were not changed. The OS page cache was warm and uncontrolled.

The original mode preserves the existing 50-query workload’s unscoped searches. The relevant mode runs the same filter against its assigned collection, so a collection sort index can cover the complete query. There are 33 exact orders across 25 first fields, including ascending, descending, ID, numeric, boolean, nested text, and composite sorts. The detailed assignments are in [the workload](workloads/musenalm-sort-mix-50.json).

All 50 cases retained their capped counts and stable pages in both modes. Seventeen cases exceeded the 10,000-result cap. The relevant mode used a declared sort order in 13 cases. The original mode reported an index for one or more collections in 13 cases, but a field order cannot use the global early-stop path unless every searched collection has that order. Only `@id` is available in every collection here.

## What dominates

- Broad unindexed sorts pay for full candidate verification and sort-key projection. In relevant mode, `annotation DESC` (#22), `created DESC` (#14), and `year DESC` (#19) each took about 5.2–5.6 seconds, compared with baseline times of 2–118 ms. The sorted paths read 245,000–268,000 source files per case, often close to twice the collection size.
- The declared title and year/title composite orders keep broad relevant-collection sorts in the hundreds of milliseconds. For example, `preferred_title ASC` (#2) took 243 ms and `year ASC && preferred_title ASC` (#5) took 232 ms. Baseline queries avoid materializing sorted records, and some filters use exact count postings, so even these indexed sorts remain slower than baseline.
- Unscoped title sorts are much slower even though `contents` has a title index: #2 took 6.04 seconds and #5 took 6.36 seconds. Other collections lack that order, forcing a full sorted scan for the cross-collection result. Collections still appear in fixed name order.
- `year` alone has a filter posting and appears in a composite sort index, but it has no single-field sort index. Broad year-only sorts (#19 and #41) took 5.17 and 2.83 seconds in relevant mode. A single-field `x-sort-index` on `year` is the clearest schema experiment suggested by these results.
- Sorted queries currently materialize a verified record for every match during a full scan, then retain only the bounded result prefix. The source read counts above identify that second materialization pass as a likely optimization target. This is an inference from the read counts and the [scan implementation](../core/src/repository/json_query/memory.rs), not a separately isolated microbenchmark.
