# Deferred desktop UI work

There is no persistent desktop UI yet. The Rust library provides source-backed views, JSON filters, validation commands, source refresh, and in-memory indexes. The CLI has both one-shot commands and a [read-only TUI](cli-tui.md) that keeps a repository handle open, builds indexes in a worker, streams search results, and loads backlinks asynchronously. The planned desktop UI will add filesystem watching, live refresh, and editing.

## Library state the UI can use today

- A lazily built in-memory picker supports repeated queries within one process. It has changed-file overlays, ordered scalar keys, per-record revisions, and deletion tombstones. `refresh(collection)` reconciles external changes by inventory; the picker also has a targeted `refresh_id` method for a future watcher or editor integration.
- The picker keeps its indexes and revisions only in the active handle. `refresh_configuration()` reports changed inputs and affected collections in that handle. `cache status` reports coverage and schema compatibility, but does not prove source freshness beyond the selected reconciliation policy.
- Views, JSON queries, and full-text searches expose query plans, metrics, and source-backed results. JSON query dependency metadata includes searched collections, paths, and a filter hash; a view result also has a view hash. These are inputs for future invalidation, not a complete query-result cache. [Full-text search](full-text.md) has word, rendered-regex, and raw-regex modes.
- `query_json_stream` and `search_text_stream` send numbered, validated page records or hits through callbacks as they become available. Workers verify candidates in parallel batches; the caller waits for each batch, then receives its hits in collection/ID order before the next batch finishes. Batch size varies by backend. Streaming can therefore show progress on broad queries, although the first hit waits for its batch. Treat hits as provisional until the call returns its total and metadata. A later source or scalar-cardinality error invalidates earlier results for that request. The CLI `--output events` exposes the corresponding record/hit, complete, and error sequences.
- `get_record` reads the original file. It reports malformed JSON immediately; a parseable record has `pending` status with a schema or `no_schema` without one. Query matches and in-memory view pages are schema-validated when a schema exists. Explicit `validate` scans schema-backed source records. Validation status and diagnostics are not persisted in the index; there are no validation workers or update notifications.
- Incoming references are discovered from source on request. For complete coverage in memory mode, request `references_to(..., complete = true, ...)`; partial coverage only includes references already observed in this handle.

## Desktop UI features to implement

1. **Open and refresh in the background.** Keep repository handles alive while the project is open. Run `warm_bigram_index`, `warm_text_index`, rebuilds, source reconciliation, queries, and explicit validation away from the UI thread. Show progress and errors without blocking navigation. Bound concurrency and cancel obsolete work.
2. **Watch relevant paths.** Watch collection directories and configuration/schema/UI files. Coalesce bursts, refresh affected collections, and recover from missed events with an inventory pass. A watcher may use targeted file refresh for individual records, then fall back to a full refresh when events are incomplete. Evict a changed or deleted record from any future source-content cache. Git status is available on demand in the file picker; it is not a source-change watcher.
3. **Show freshness honestly.** Distinguish a returned result, a result awaiting source verification, and a result verified under the selected freshness policy. Memory indexes are process-local. Do not present an older snapshot as current after reconciliation fails.
4. **Patch visible views after changes.** Reexecute affected requests and compare by collection and record ID. Apply value, membership, ordering, page-boundary, and total-count changes while preserving selection and scroll position where possible. Query dependency metadata can help decide what to rerun, but the current library does not maintain live result subscriptions.
5. **Reject obsolete asynchronous results.** Tag requests with view identity, parameters, and a request ID. A slow earlier filter, sort, or prefetch result must not replace a newer one. Cancel where practical and discard late results otherwise.
6. **Prefetch selectively.** Hover, focus, adjacent pages, and idle time can warm likely next records or collections. Delay fleeting requests, deduplicate work, and cap memory and I/O. File-access frequency may improve prefetch or ranking in a persistent session; it must not change structural query membership or deterministic ID ordering.
7. **Present record state and diagnostics.** Show `no_schema`, `pending`, `valid`, `invalid`, and `incorrect_json` distinctly. A malformed record can appear in standalone word or regex search results and provides its ID/path, raw bytes, size, and modification time; field paths cannot be verified. `get_record` also returns malformed source files. To show schema diagnostics for a parseable `get_record` response, the UI needs an explicit validation path or a library change that validates that response in all modes. Do not infer validity from typed cache keys.
8. **Use phase timings for troubleshooting.** Display useful counters and timings from library responses. On project close, unsubscribe watchers and cancel jobs; closing the process releases its derived index.
9. **Index scalar-cardinality violations.** Record which source IDs have multiple values at a path used as a scalar, and update that information on edits and deletes. Queries currently scan beyond a full page when a later invalid array could cause a scalar-cardinality error. A reliable violation index would let these queries stop after the page while retaining the same error behavior. Define how nested paths and `OR` branches are tracked before using it for early completion.
10. **Cache frequently scanned source bytes.** Count files actually verified, whether served from source or cache, including false positives; do not score IDs selected by an index but never reached because pagination stopped. Use frequency and recency for admission and eviction. Keep the content-cache byte budget at or below 15% of memory available to the process (respecting container limits), including allocation overhead and page-rounded mappings; do not set an arbitrary file-count cap. Pack small files in owned byte storage. Map larger files only when their backing bytes can be guaranteed immutable for the mapping's lifetime: a watcher and metadata checks detect changes after they happen and cannot by themselves make an in-place edit safe for mmap. On Linux, inspect `/proc/sys/vm/max_map_count` at runtime and reserve headroom for other mappings; the [documented common default is 65,530 virtual-memory areas per process](https://www.kernel.org/doc/html/latest/admin-guide/sysctl/vm.html#max-map-count), not 65,530 cached files. Benchmark warm queries with and without the cache before enabling it by default.

## Later acceptance checks

- External edits, deletes, renames, configuration changes, event bursts, and missed watcher events reach visible results without requiring a full scan on every interaction.
- A changed record can enter or leave a filtered page, move under a sort, alter a total, and update an incoming-reference view correctly.
- Rapid navigation and cancellation never display an obsolete response as the latest one.
- Background jobs report useful progress and failures; pending schema status is not mistaken for valid or invalid.
- Index rebuilds and invalid source files preserve the authoritative JSON files.
- Repeated candidate verification benefits from the byte budget without retaining stale content, exceeding the effective-memory ceiling, or exhausting OS mapping limits.
