## 1. Pack small registered files together and schedule independent files concurrently

**Observed.** In `crates/core/src/construction/initial.rs`, lines 849–885, a registered streaming reader causes the collection's file list to be divided into one-file jobs. With several eligible small files and multiple workers, `stage_small_stream` creates a fresh collection admission per file and seals its tail at EOF (lines 55–115). The coordinator runs at most four callbacks, collects the entire window and then calls `publish_initial_segments` once per file (lines 1241–1319). Eight one-record files therefore create eight one-record drafts and eight content publications even if the record and file targets are both eight. Subsequent consolidation cannot recover the work already performed.

Large stream jobs are processed synchronously by the outer loop (lines 910–931 and 994–1018). The grouping of small registered files is handled afterward. One slow large registered file can therefore delay even the start of an independent small registered file. The separate shared-binding loop shrinks any batch containing a registered stream to one file and walks files and bindings synchronously (lines 1324–1359, 1397–1412, 1449–1459). Parallel decoding inside one file and parallel framing of different files are distinct capabilities.

**Implement.** Use bounded groups of independently eligible files. Let workers frame and decode. Give the collection coordinator ownership of admission across file boundaries. A completed small file can contribute its tail to a draft with other completed files that share the necessary binding set. Seal according to record count, distinct file count and actual resource bounds. Permit private full segments for large files. A physical file becomes visible only after its EOF, checks and all required bindings succeed. Publish eligible groups together. Allow a ready independent group to publish while a slow group is outstanding. Preserve stable byte ranges, generated IDs and per-file diagnostic order. Applications have no callback-order guarantee. Keep the existing repository worker pool and bounded work in flight. Do not buffer all contributions from a large file while waiting for a group.

**Acceptance.**

1. Through the public registry, index 64 one-record files with the same binding, four or more workers, target eight and file limit eight. For a homogeneous successful run, expect eight segments of eight. Count actual root installations containing new records. They should be bounded by the number of full segments in this fixture. Exclude initial empty and final bookkeeping revisions. Repeat with file limit one to prove the real file boundary still works. Check file reverse membership, record IDs and exact byte ranges.
2. Use two independent registered files above 8 MiB, then one above and one below. Hold one callback after it announces entry. Using a bounded observation in the harness, show another independent file enters and can reach a searchable revision before release, when scheduler credits permit. Release the gate on every test exit. Repeat with one worker for ordinary completion. Keep any particular filename or callback start order out of the public contract.
3. With two bindings on the same file, hold one binding, complete an independent file, then exercise success and a fatal binding. Every observed view must contain either all the shared file's required memberships and records or none. An already published independent group survives the failure. Record actual active callbacks separately from active decoders.

## 2. Respect segment targets for readers that return multiple ranges from a whole document

**Observed.** Managed whole-document preparation takes the ranges from `frame_outcome`, groups up to 256 ranges or roughly 1 MiB, then builds one contribution per group. It does not use the configured record target. The large whole-document initial path has the same fixed limits. The small ordinary initial path can build one contribution across the entire worker batch. An empty `SegmentAdmission` accepts the first contribution in full. Ten distinct short records from a registered, non-streaming reader therefore reach a fresh managed segment as one contribution of ten even with `target_records = 4`. The reader has already supplied ten independently decodable ranges. The input provides all the boundaries necessary for 4, 4, 2. The checked 100,000-record registered example implements the separate streaming interface.

**Implement.** Carry the segment policy and remaining draft capacity into range partitioning before local slots, postings and diagnostics are built. Apply it to normal initial construction and managed add/replacement, including public conditional replacement. Check ordinary many-file jobs when the independently configurable file limit exceeds the record target. The worker's I/O batch size may exceed one segment. Changing the input read size or shrinking every ordinary job to one file is unnecessary. Preserve half-open file offsets, per-file diagnostics and the single file-revision publication. Retain the supported whole-document buffer for readers that require it and the existing oversized-single-record handling.

**Acceptance.** Register a reader that implements only the ordinary framing interface and returns ten short ranges with distinct IDs. Set target four and max files one. Run fresh build, managed add and replacement. Inspect the new file's segment membership immediately after each operation. Expect 4, 4, 2 where the file is the sole member, ten correct locators and one catalog membership. Include a target crossing the 256-range work-batch boundary, e.g. 310 records at target 100 producing 100, 100, 100, 10. Add a small-file fixture of ten ordinary one-record files with file limit greater than ten and target four. Verify query, reverse lookup and pinned-view behavior as well as geometry.

## 3. Remove expensive file work from the writer lock used by direct publication

**Observed.** `replace_file` takes `self.0.writer` at line 807 of `lifecycle/mutation/mod.rs`. Within that scope a verified update calls `verify_old_content` (line 879), stages replacement and may call `compact_verified_base` (line 895). Verification digests the old byte buffer, reconstructs its contributions, scans file layout and sorts the comparison. The reconstruction helper hashes the same old byte buffer again. The verified scan limit is applied after reconstruction and comparison. Independent direct publication takes the same mutex at `lifecycle/publication.rs:1123`. Its receipt must wait for this work. The existing test pauses the new file's reader earlier in preparation. It cannot detect this later serialization.

Whole-document adds also acquire the writer before `stage_prepared_add`; the contribution-backed branch of `index_prepared_file` finalizes native segments there. Pre-indexed streaming segments follow a cheaper path. On platforms using the digest fallback, `verify_current_source` can perform an entire file read inside this writer scope.

**Implement.** Prepare reusable document segments, digest evidence and logical layout against a pinned view outside the writer lock. Reuse the already computed digest for reconstruction. Use the file's existing segment routes when collecting old ownership. Check cheap eligibility and supported maintenance limits before constructing an index that would be discarded on fallback. Where only record layout is needed, obtain IDs, ranges and classes without building unused posting families, provided the same schema and identity rules apply. Root-dependent compaction can be prepared privately against a specific root. Revalidate its dependencies at handoff, rebase the logical replacement or safely retry the physical plan. Preserve file incarnation, owner, logical key, identity, revision and unchanged-result checks. Continue to allow the documented append fallback when verified removal is ineligible. Do not install a compaction plan built for a stale root.

**Acceptance.** Modify a file using its correct old-byte hint. Pause inside old-layout reconstruction, after new-file parsing has finished. Submit an unrelated direct record and require its receipt to succeed before releasing the file operation. Verify both final owners and a view pinned before the replacement. Repeat while pausing whole-document segment finalization during add. Count full old-buffer hashes on successful verified reconstruction and expect one. Exercise wrong bytes, concurrent replacement of the same file and an unrelated publication during private compaction. For the no-identity fallback, use a test seam to check that holding a verification read cannot hold up direct publication.

## 4. Bound memory while files are being framed and measure the simultaneous peak

**Observed.** A registered framer passes an owned chunk to `emit`. The coordinator first requests shared byte credit in `schedule`, after the byte vector has been allocated. Built-in JSONL reads the first chunk and later prefetches another before requesting shared credit. Concurrent managed calls prepare before taking the writer mutex. Consequently several callers can each hold a full chunk waiting for the same credit. Large single-record chunks amplify this difference. The current credit limit bounds scheduled chunks; it does not bound all input already framed and held by concurrent callers.

The generic path records its local peak before draining for capacity. `BuildScheduleStats::absorb` then takes the maximum of per-file peaks. A maximum over per-file peaks cannot represent simultaneous usage by several active files, and the pre-drain calculation can include a pending chunk that never had a reservation. The single-file benchmark remains useful for its own workload.

**Implement.** Account separately for active framers, pending input, admitted decoder work, completed intermediate results, and finished private segments. Establish a repository-wide bound on entering the framing phase, with room for producer scratch and bounded lookahead. For core-controlled framing, obtain capacity before materializing the next chunk where practical. If a growing single record exceeds reserved space, define controlled growth, single-oversize admission or a supported resource-limit outcome without starving existing work. The registered callback currently owns its own allocations while framing. State the boundary of the guarantee: the core can cap concurrent callback admission and its own buffers; a byte-exact limit on arbitrary third-party allocations requires a cooperative allocation or reservation contract. Do not present an estimated callback allowance as measured RSS. Instrument aggregate high-water at shared acquisition/release points, including cancellation and failure. Avoid duplicating a whole chunk merely to measure it.

**Acceptance.** Use several concurrent managed imports, a small configurable test allowance and a gate holding the oldest decoder. Measure simultaneous framed-but-waiting bytes and charged work separately. Adding waiting callers must not multiply the permitted number of active framers or retained core buffers. Repeat with oversized single records. Exercise one worker, a late fatal result and a retry. Verify all credits return to zero, callbacks complete or receive the documented error and no incomplete file becomes visible. For two overlapping bounded ordinary chunks, verify a shared peak reflects actual overlapping allocations.

## 5. Preserve configured path eligibility at initial publication

**Observed.** `verify_initial_files` uses `fs::metadata(root.join(relative_path))`, compares revision and available creation time, and requires object identity. This follows a symlink. Discovery separately implements `Skip` and `FollowWithinRoot`. Object identity can still match when a previously selected path now resolves through a symlink to the same file. The initial handoff then accepts a path the configured discovery policy would now exclude. This is distinct from an ordinary content replacement with a different inode, which the new revision check catches.

**Implement and verify.** Reuse the existing selection and containment rules when verifying publication eligibility. Handle intermediate path components as discovery does. Deduplicate checks by observed file and effective selection rules across a publication group. Keep cheap metadata checks on normal paths and retain the documented explicit unverifiable outcome where object identity is unavailable. Exercise an in-root path reorganization between preparation and publication with both symlink policies. Compare the handoff result with a fresh discovery using the same rules. A failed candidate publishes no records or metadata changes. The usual filesystem race after the final successful check remains part of the observation contract.

### Scope of the measurements

Pending input accounts for observed Rust buffer capacity. The admitted column charges decoder work through ordered admission, including completed contributions waiting their turn. The combined column measures their simultaneous peak. Private index-family bytes are estimates, and process peak RSS is recorded separately. The core caps concurrent callbacks and the input it accepts from them. Third-party readers control allocations made inside their callbacks before they emit. Built-in JSONL permits bounded lookahead and stops with an explicit source error if a line would exceed 128 MiB. An oversized permitted chunk uses the decoder window alone.

The default skip-symlink path checks source components and reuses the leaf metadata. Follow-within-root re-runs alias selection once per distinct selection in a publication group to match discovery's deterministic choice. The filesystem can still change after the final observation. Linux object identity and the forced digest branch were exercised on this host.
