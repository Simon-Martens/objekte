# Musenalm benchmark for Objekte and Tantivy

## Assignment

Implement and run a reproducible Rust benchmark comparing `objekte-search-core` with the upstream `tantivy` crate on the same Musenalm files. Answer two questions for each compatible query. How long does each engine take to obtain an exact count? How long does it take to return the requested ordered page together with that count? Report index construction time and memory alongside query cost so the cost of making a query fast is visible.

Deliver the runner, compatibility inventory, regression fixtures, and one measured release report on `integration/musenalm-tantivy-benchmark`. Follow `AGENTS.md` and `docs/ai/README.md`. Work in a sibling integration worktree, push each commit, and leave the merge to the user. The benchmark-only Tantivy dependency and its lockfile changes are part of this assignment.

## Measurement contracts

Classify **predicate compatibility** and **page compatibility** separately. Save the original request, the effective request and every changed option. The following two contracts have different meanings and get separate tables.

| Contract | Objekte operation | Tantivy operation | Required equality |
|---|---|---|---|
| `predicate_count` | Bind the source case, preserve its collection, filter, FTS, parameters and clock. On the bound request select count, zero limit and offset, locator mode, evidence off, and clear ordering. Call `IndexView::search`. | Run the equivalent typed query with the `Count` collector and scoring disabled. | Exact total, zero returned rows, and prior verification of the complete matching membership. |
| `ordered_locator_page` | Preserve the effective sort, offset, limit and exact count. Request locators with evidence off. Read the returned page through the normal public API. | Use one search with count and bounded ordered collection where possible. Materialize each winning locator through the Tantivy index. Include this retrieval inside the timer. | Exact count and exactly the same ordered sequence of `(collection, record_id, relative_path, byte_start, byte_end)` for the requested page. |

The second contract measures the common locator projection. Most historical cases ask for matched-field evidence. Q137 asks for bytes and Q138 asks for a logical record. Identify such rows as projected in the report. Never publish a locator projection as the latency of producing evidence or payloads. If two cases yield the same effective request within a schema mode and contract, measure it once and list its source IDs as aliases. For example, Q134–Q136 collapse in count mode but represent three different page offsets. Q137–Q139 collapse when projected onto the same locator request.

The default tie-break in the inspected ranking code is ascending `(collection, record_id)` after the requested keys. Apply it on both sides, including queries without explicit sort and ties at deep offsets. A benchmark-built numeric identity ordinal is suitable as the final fast-field key if it is assigned in this order, independent of ingestion order. Charge its preparation to the Tantivy build. Retrieve actual winner identities and locators. Segment-local document IDs, relevance order and sorting 50 arbitrary hits after collection cannot implement this contract.

## Compatibility inventory and implementation order

Load and bind every source case before applying projection. Drive translation from the parsed request and a small field-capability table. Handle unknown operators explicitly. Maintain one inventory row per source ID with the schema mode, predicate family, representation, status and reason for each contract, and effective measurement ID. Report three distinct outcomes: compatible and verified, unsupported with a semantic or implementation reason, and failed verification. A disagreement on a promised mapping is a failed run.

Implement ordinary structured filters first, then literal FTS and mixed cases, then pages. These groups give an informative comparison even if specialized operations have no equivalent.

Each index must support a different literal or range bound using the same code. Keep direct native typed queries and queries using derived text/structure fields distinguishable in the report. There is no requirement to implement joins, an Objekte interpreter inside Tantivy, or an alternative search backend for the application.

Publish the index definition used for each engine, including indexed paths, field types, fast fields, text analyzers and derived fields. Use the same definition for quick and full runs within a schema mode. If Tantivy has a field materialized that Objekte scans from source, identify that difference on the affected rows. The resulting time and space tradeoff is part of the benchmark.

### Exact literal search in Tantivy

A practical implementation uses overlapping case-sensitive bigrams with indexed positions. Emit a bigram at each consecutive Unicode scalar start, with byte offsets into the decoded value and increasing positions. For a two-scalar needle, issue one term query. For longer needles, issue a zero-slop phrase over consecutive bigrams. Use a separate single-scalar term field for one-scalar searches. Index all scalars generically. Preserve punctuation, whitespace, case, field scope and value boundaries. Separate repeated values with a position gap so no phrase can span two fields or array elements. Derive global and path-scoped text from the exact logical segments in the selected Musenalm registration.

Tantivy's stock `NgramTokenizer` documents position zero for every gram of a value. Its offsets alone cannot support this phrase construction. Use a small benchmark-local tokenizer with advancing positions, or a demonstrably equivalent native term-dictionary approach with checked term-length limits and newline handling. Choose one implementation for the reported run. A Boolean conjunction of grams is only a candidate filter. If the chosen approach needs residual verification, charge all candidate retrieval and verification to that engine's query time and label the method. Do not call the Objekte search engine to complete a Tantivy query. [Tantivy tokenizer](https://docs.rs/tantivy/latest/tantivy/tokenizer/struct.NgramTokenizer.html) · [Phrase query](https://docs.rs/tantivy/latest/tantivy/query/struct.PhraseQuery.html) · [Regex query](https://docs.rs/tantivy/latest/tantivy/query/struct.RegexQuery.html)

## Running and measuring

Provide a single documented entry point. This interface is suitable:

```sh
python3 bench/run_musenalm_tantivy.py quick --root examples/musenalm --result-dir bench/results/musenalm/tantivy-quick
python3 bench/run_musenalm_tantivy.py full --root examples/musenalm --result-dir bench/results/musenalm/tantivy-full
```

Resolve and build the release binary once with the lockfile. Accept `--cases`, `--query-workers`, `--build-workers`, `--repetitions` and a fresh result directory. A selected case that is unsupported must appear with its reason. Unknown IDs, invalid settings, missing samples and parity failures must produce a nonzero exit.

Use the same physical fixture path for both processes, including when the integration worktree is separate. Establish the same source-file cache condition before each measured build, preferably by priming both from the shared inventory, and record it. Use the same explicit build-worker budget where supported and record any effective limit. Keep verification in a separate pass so its large membership allocations do not inflate reported engine RSS.

- **Construction.** Time from opening/discovering the source through a complete searchable index. For Objekte use `Index::start_build(...).wait_complete()` and pin the resulting view. For Tantivy include source reads, JSON parsing, projections, index writing, commit and reader readiness. Settle writer/merge activity before query timing and record that cost and the final segment count. Use the ordinary in-memory Objekte build. A Tantivy RAM directory gives a comparable primary build target. Name each storage mode explicitly. Record elapsed time, build worker budget, writer memory, peak RSS, resident memory at query readiness and any measurable index byte size with its definition. One measured build per engine/schema configuration suffices for the first report. Label it as one observation.
- **Query measurement.** Run each engine in its own release process, sequentially on the same host and CPU allocation. Use one query worker per engine by default. Allow an equal explicit worker budget for a subsequent parallel run. Apply the setting to the actual search executor. Record effective workers, build workers and CPU affinity. Use Objekte's default ASCII index as the named primary alphabet, verified-result cache set to zero, and no harness result cache on either side. Keep normal index structures and the OS page cache warm. This measures repeated searches on open indexes.
- **Timing boundary.** Construct equivalent query objects and bind request parameters outside the clock. Start immediately before the ordinary search call. Include engine planning performed by that call, matching, scoring-free collection, ordering and requested winner retrieval. Stop when the contracted result is available. Oracle evaluation, digest creation, diagnostics, JSON output, process startup and index construction are outside that interval. Consume returned values. Use a monotonic timer and record nanoseconds.
- **Run length.** Quick mode uses representative cases such as Q001, Q030, Q035, Q044, Q054, Q081, Q116, Q136 and Q144, one warm-up pass and one timed pass. Full mode inventories the entire suite, warms every eligible request once and records seven timed repetitions by default. Use the same seeded case permutations on both engines and report engine order. Run the reversed engine order when a close result or drift changes the interpretation. Reuse indexes within a process and existing valid oracle evidence across runs. Do not repeat a full build or file scan for each query.
- **Reporting.** Keep raw samples. For each eligible contract show QID/aliases, query or short predicate, collection, representation, match count, offset/page length, sample count, each median in µs or ms and `Tantivy median / Objekte median`. Ratios above 1 mean Objekte was faster. Show variability, such as min–max or interquartile range. Group the report by query family and contract. State coverage out of 150 historical and 70 additional cases at this revision. Keep exclusions, verification failures and equivalent projections visible. Avoid a single overall speed claim dominated by duplicate requests or by the number of examples in a family.

### Limits and deviations

The first result covers 104/150 historical and 4/70 additional predicates. The inventory explains unsupported cases and page sorts independently. Text/compound sort, complex string operators, metadata facts, relation traversal, and other extended forms were not mapped. Pages requesting evidence or payloads were projected to locators; their timings cannot be used as evidence or payload latency. Objekte's public in-memory API does not expose a comparable index byte size. Tantivy's 180.3 MiB is managed RAM-directory segment-file size, not full process memory. The numeric-domain diagnostic found no distinct decimals collapsing to the same `f64` representation or integers above 2^53 in this fixture; it does not cover future data. Build timing has only one observation per configuration. The comparison is against two engines on this revision and fixture; no base-revision Tantivy result exists for a before/after comparison. No core behavior changed, so the new full comparison is the performance benchmark relevant to these changes. No separate issue was required for the documented unsupported mappings or limitations.
