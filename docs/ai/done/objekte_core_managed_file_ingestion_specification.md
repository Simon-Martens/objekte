## 1. Public ingestion contract

| | File import | Direct record submission |
|---|---|---|
| Application supplies | Catalog root, registered format reader and collection selection rules, then a path to import | Registered source, logical ID, typed value, optional searchable text and, for a versioned provider, its record version |
| Format or provider supplies | Zero or more logical records, raw byte spans and any intrinsic IDs or reader-defined text needed by the configured representation | Retained data, or version-checked provider access under the existing direct ingestion contract |
| Objekte owns | Opening the file, observing its identity and metadata, coordinating the reader, validating ranges and identities, publishing records and catalog indexes | Admission, publication, indexing and the existing retained/provider payload behavior |
| File lookup and metadata | A live catalog file and its records are reachable in both directions | No file, no range and no entry in any file metadata index |

## 2. The file reader and publication

1. **Open and observe.** Resolve the path under the configured root with the existing path representation, containment, symlink and collection-selection rules. Open the selected file. Obtain its size, modification time, available creation time and filesystem object identity from that handle. Discovery metadata is a scheduling hint. `SourceRevision` describes an observed source, `FileVersion` is the index-local incarnation, and `FileId` is the catalog identity. Keep all three meanings distinct. Preserve native path bytes and existing query-path encoding.
2. **Decode the observed bytes.** Invoke the registered `SourceReader` on borrowed bytes or bounded input chunks from that open file. Keep existing `frame`/`parse` readers working via the existing/default adapter. Expose a format-neutral way for a multi-record reader to emit records incrementally where the current extension point is insufficient. Use the current JSON and bounded JSON Lines machinery. A third-party line- or block-framed reader must be able to stream without claiming to be JSON Lines. A one-record or whole-document format can continue to use a contiguous buffer.
3. **Define the emitted record.** The callback provides the typed record and its half-open byte span `[start, end)` in the original file, plus configured text or intrinsic identity as appropriate. Chunk-local offsets are converted to absolute file offsets exactly once with checked arithmetic. Preserve the existing framing rules for ordering, overlap, logical empty ranges, delimiters, malformed records and empty-file fallback. Boundaries must recover the same record through the registered reader's query-time decoding contract. Preserve schema conversions, representation versions, text coverage, projections, diagnostics and raw fallback. Core applies the collection's configured intrinsic, generated, filename or relative-path identity policy. A callback never needs to stat or reopen the path, allocate slots or maintain indexes.
4. **Prepare outside the publication lock.** Feed outcomes into the repaired segment builders. Stage finished segments privately with one candidate catalog revision and the applicable file-to-record routes. Reuse buffers and bound outstanding input by the chunk/worker budgets plus the largest indivisible record. The final index necessarily grows with the record population. A long stream must not also retain all its decoded values, frame ranges or input bytes before it can build segments. Share the stable observed input across applicable collection readers where practical. Account for each decoder that genuinely needs to run.
5. **Validate and publish.** Check the open file after reading. At handoff to publication, verify that the path still resolves to the observed object and revision, and validate the expected live file incarnation, path ownership and record ID conflicts against the current index view. Use existing platform support for filesystem object identity, such as device and inode on Unix. Modification time and length alone cannot distinguish two files with the same stamp. When a platform lacks a reliable identity, use a verified content comparison with current metadata or return a specific stale/unverifiable result. A required digest can be accumulated while consuming the input. Never hash or reopen a whole file once per record.
6. **Handle intervening changes.** If the source changed, discard the staged attempt and retry within the lifecycle retry policy or return its stale/conflict outcome. Reader contract errors, ID collisions and cancelled work publish no partial file. Existing malformed/unreadable outcomes remain intentional reader and catalog behavior. Publish one complete file revision, all its participating records across segments/collections, memberships and metadata indexes in a single index publication. Initial discovery may expose its existing pending catalog state. It must be distinguishable from a completed import. Other files and completed direct records remain queryable during preparation. Reuse valid staged work across unrelated direct publications when its preconditions still hold.

The filesystem can change immediately after a successful observation. This contract guarantees that an accepted revision's fields, locators and file metadata describe the same observed input. Document the existing limitations for in-place writers that deliberately preserve all observable revision markers. For lazy reads requested by a pinned view, verify the source against that view or use retained old content where supported. Return the existing unavailable/stale result when the requested bytes cannot be recovered. A pinned result must never silently return newer bytes for an older indexed value.

## 3. Catalog, indexes and query semantics

One physical file as defined by the existing catalog path/identity rules has one live catalog entry, including a successfully imported file emitting zero records. Use the pinned catalog as the authority for path, ID, source revision, optional creation time, status and participating collections. Record slots carry the file reference and their own range. Store membership compactly by collection/segment and intersect with liveness. Preserve sufficient revision information for safe rereads. Avoid copying paths, timestamps and scalar metadata postings into every record.

| Query or access | Required behavior |
|---|---|
| Path → file and `FileId` → file | Reuse existing lookup tables. Native path lookup, query-path equality/range behavior and the public catalog agree on the same publication. |
| Record key → file and file → records | Direct lookup of a live file-backed record gives its file and range. A live direct record gives `None`. An unknown record is distinguishable from a known direct record. Reverse lookup yields exactly the live keys for that file, optionally scoped to one collection. A known empty file yields an empty result. |
| Size, modification time and creation time | Provide indexed equality and ordered range access at file granularity. Reuse suitable base/delta or ordered indexes from the repaired implementation. Store one live membership per file per applicable scalar index, including ties between files. Account explicitly for unknown creation time. Update only affected entries on add, replacement, move and retirement. |
| Metadata filtering | Resolve matching file IDs once per pinned query restriction and project through the existing file-to-live-slot routes into the current collection and candidate domain. Reuse that result across segments where applicable. Selective supported lookups must avoid scanning all catalog files, records or unrelated segments. Broad predicates may take the cheaper traversal. Metadata-only membership, counts and locator access require zero file or provider content reads. |
| Direct records | Every `@file.*` field and `@record.byte_start`, `@record.byte_end`, `@record.byte_length` is missing. An imported file with unavailable creation time has the existing explicit null `@file.created`. Keep the distinction in state predicates, results and sorting. `@record.id`, collection metadata and ordinary fields remain available. |
| Boolean composition, sort and pages | Apply the engine's existing missing-value and three-valued Boolean semantics to each record. A file-only leaf cannot eliminate a true direct-data branch of an OR. Compare negation, inequality, missing/null checks, metadata sort keys, ties, pagination and match evidence with the exact evaluator. Fileless records participate in an unfiltered metadata sort using the existing missing-value order. |
| Payloads | File-backed bytes are the validated original range. Retained direct records keep their logical payload and `OriginalBytesUnavailable` behavior. A versioned direct provider may return its own original bytes. This grants it no file identity. |

Use the existing shared data indexes for FTS, typed fields, sorting and relations. Preserve per-source coverage guarantees when a format supplies its own text representation. Keep cache keys, estimates, filtering and sort resolution consistent with the pinned view after a file move or update. Query-time file metadata refers to the indexed observation, so editing the filesystem alone does not alter a pinned catalog.

## 4. Mutations and compatibility

- **Identity and ownership.** A logical record key is collection-scoped. Simultaneous insertions of the same key from different routes cannot create two live records or silently transfer ownership. Validate direct replace/delete against the owning registration and file updates against the owning file. Preserve existing identity rules for a replacement of the same file. An intentional transfer can retire the old owner and insert via the other route. Exercise both directions and failed collisions.
- **Move, update and delete.** Preserve the fast route for content-preserving compatible moves. Update path lookup and applicable metadata/sort keys. Recompute identities or memberships when the configured path-based policy or collection selection changes. Replacing a many-record file retires exactly the superseded keys and installs its new set. Deleting a file retires only its file-owned records. Direct records beside them survive. A touched-file operation must not reconstruct the whole catalog or unrelated segments.
- **Compaction, rebuild and reconciliation.** Preserve backing ownership, identity routes and liveness across base and delta segments. Reconcile disk changes only for registered file sources. Keep direct records through reconciliation and rebuild according to the repaired contracts. A pinned view keeps its previous catalog plus its own logical visibility while the new view advances. Respect the existing limits of supported persistence modes.
- **Migration.** Document the removed direct-link calls with a working replacement for each use case. Import the saved file through a registered reader when it owns the record. Submit the value directly when the application owns it. Store a navigation path as ordinary application data when that is all the application needs. Check whether any *supported durable* format can contain the previous hybrid form. If so, retain enough information to preserve direct values/provider identity as fileless, or return a versioned diagnostic with a recovery procedure that preserves the authoritative records. Never reinterpret an old linked direct value as an authoritative file slice. Transient session spools follow their existing ownership and cleanup contract.
