# Record ingestion and optional file catalog for Objekte

## Assignment

Restructure `objekte-search-core` so a registrar can declare a schema, submit typed records in batches and search them without a filesystem root, filename, byte range or JSON conversion. A registrar that works with files can attach an optional `FileCatalog`. The catalog maintains file identities and their relations to records in both directions. All sources use the same segmented indexes, planner, residual predicate evaluator and publication lifecycle.

Deliver the implementation on `integration/record-ingestion-and-file-catalog`. The design was checked against `master` at `d8d703dbd24e1ef72f9a37cf7a235a7a559e0598`. Pin the integration base before any production edit. Section 10 defines the mandatory baseline, final rerun and release decision. If the local base already contains part of this refactor, use the last clean ancestor for the before run and record both SHAs. Read `AGENTS.md` and `docs/ai/README.md`. Use the sibling worktree `../objekte-integration-record-ingestion-and-file-catalog`. Make each implementation stage reviewable and compilable, push after each commit, and leave the merge to the user.

**Scope boundary.** Deliver the public adapter interface, working direct ingestion, optional catalog, helpers, existing file adapter migration and workspace caller updates. Keep JSON and JSONL implementations in the core crate for this assignment. Their eventual separate crate, real XML/JSON-LD adapters, new file watching or callback services, a durable ingestion log and a new on-disk index format are follow-up work. Preserve existing file mutation, refresh and reconciliation behavior. The Tantivy comparison is an independent assignment.

## 2. Ownership and module layout

Use the following ownership boundaries. Move implementations in stages. Preserve existing public import paths with thin re-exports where their semantics still hold. Avoid a repository-wide move of unchanged code merely to make a tree diagram exact.

| Owner | Contents and dependency direction |
|---|---|
| `model`, `schema`, `repository::configuration` | Existing logical types and schema. Introduce a source-neutral collection declaration containing name, schema and query/index policy. Keep file-root, suffix, framing, and filename identity in file source configuration. |
| `records` | Logical record identity, collection-scoped record keys, public record metadata, and the internal read projection/backing interface. Internal addresses use the existing segment and slot types. This module can express optional provenance without importing a JSON parser or opening files. |
| `ingestion` | Registration handles, owned input types, batch builder, writer, receipts and queue errors. Private submodules `queue`, `spool` and `publication` own admission order, optional overflow storage and the handoff to the existing coordinator. |
| `files` | Public `FileCatalog` registration/service handle, pinned `FileCatalogView`, checked file references and record–file lookups. Put catalog state, file discovery, range access, file preparation, file mutation and reconciliation under this ownership. Existing lifecycle entry points may delegate to these implementations. File-only hot paths may use private file types. |
| `adapter` and `adapter::helpers` | Public contracts needed by an external registrar or reader. `helpers::json_string` contains reusable JSON string decoding. `helpers::case_fold` exposes the exact shared Unicode fold. Each helper has a narrowly named module and an independent test. |
| `source` / existing built-in readers | Keep `SourceReader` and registered file decoding available through the adapter-facing API. Keep JSON/JSONL framing, syntax, source-specific optimizations and raw fallback on the adapter side. Preserve the current built-in convenience constructors. |
| `construction`, `index`, `query_*`, `lifecycle` | One logical construction, index and search implementation. Lifecycle owns publication and synchronization. File services and registrars submit changes through it. Query planning sees logical types, index capabilities, active slots and proofs. |

Distinguish three identities. **Record key** is `(CollectionId, RecordId)` and addresses a logical record. Existing public name/ID lookup remains available. **Physical record address** identifies a segment-local slot in one pinned publication; compaction can remap it. **File identity** is a catalog-scoped `FileId`; a path can change without changing that ID. A provider version used for rereading a record is different from all three. Keep existing file, record and publication revision types distinct.

Each segment groups one registrar and compatible record backing. Select the backing once per segment for scanning. Use compact slot-indexed side tables for source-specific data. Keep the common record header small and avoid adding a path, optional timestamp set, virtual reader or reference-counted file object per record. A collection and an index may have segments with different backings. Consolidate compatible groups, and leave incompatible groups separate. Counts, sort order, relations and paging must still span them.

## 3. Public API to deliver

Use the public names and call sequences below and the decisions in section 3.1. Reuse existing identifier and error types at unchanged boundaries. The implementation agent owns private function decomposition and Rust lifetime spelling. Changes to record ownership, public semantics, queue limits, ordering, verification or benchmark gates require a reported design conflict. Include compiling Rustdoc examples and a downstream integration test using public imports.

```rust
let mut schema = Schema::default();
schema.register_field(FieldDefinition {
    path: vec!["year".into()],
    kind: LogicalType::Number,
    required: true,
    nullable: false,
    indexed: true,
    multi: false,
    element_nullable: Vec::new(),
})?;
let value = Value::Object(BTreeMap::from([
    ("year".into(), Value::Number(Number::integer(1808))),
    ("title".into(), Value::String("Almanach für 1808".into())),
]));

let mut builder = Index::builder();
let entries = builder.collection("entries", schema)?;
let provider = builder.register_records(entries, "application.entries", 1)?;
let index = builder.build()?;                 // usable empty index, no path required
let writer = index.ingestion().writer(provider)?;

let mut batch = writer.batch();
batch.insert("entry-47", value)?;             // value is an owned core Value
let receipt = writer.submit(batch)?;
let revision = receipt.wait_published()?;
let view = index.view()?;                     // includes at least that revision
let hit = view.get_record("entries", "entry-47", ReturnMode::Logical)?;
```

- Use existing `Value`, exact numeric semantics, nested objects, array cardinality, null/missing distinction and schema validation. A declared field remains queryable when its index is disabled. Use `Schema::default` and `register_field` directly for this assignment. Keep one schema and index-policy implementation.
- The reader registration lifetime is pinned by each searchable view; reader/cache identity is the tuple of collection, adapter ID, adapter version and representation version. An index-scoped registration binds a collection, stable adapter ID/version, text representation and record access policy. Distinct registrations may produce records in one collection. IDs must be unique among live records within that collection. The registration that owns a live record controls its replacement or deletion. Detect foreign handles, duplicate inserts, and missing replace/delete targets. Keep insert strict; add explicit `replace` and `delete` operations to the batch. Reject conflicting operations for the same key in one batch. Across batches, apply in admission order.
- Register `FileCatalog` explicitly on the builder when needed. Give opted-in registrars a scoped capability to declare or reuse a physical file and link records in the same publication operation. Support many records per file, shared files across collections, and records with no link even when a catalog is installed. Treat declaration of collection/registrar/schema as fixed for the lifetime of this index configuration. The existing file-opening API wires up the service automatically for file users. Ordinary record registration has no required extension, repository path, environment lookup or discovery pass.
- Give callers an input for an owned logical value with optional adapter-declared text segments and optional file provenance. Also allow a decoded value to be moved into construction and discarded after indexing when its registered source can reread it. The public registration and write surface must not require internal segment, bitmap, scheduler or bound-predicate types.

A registrar can explicitly associate an owned record with a file. This example uses an existing file-backed repository root. `declare_file` stages a catalog entry from checked metadata or reuses the existing matching entry. A local file token is valid only in its batch. The record remains independently owned in this example.

```rust
let catalog = builder.register_file_catalog(FileCatalog::new(root)?)?;
let registrar = builder.register_records(entries, "import.entries", 1)?;
builder.enable_file_links(registrar, catalog)?;
let index = builder.build()?;
let writer = index.ingestion().writer(registrar)?;
let mut batch = writer.batch();
let file = batch.declare_file(relative_path, observed_file_revision)?;
batch.insert_with_file("entry-47", first_value, file, Some(first_range))?;
batch.insert_with_file("entry-48", second_value, file, Some(second_range))?;
writer.submit(batch)?.wait_published()?;

let view = index.view()?;
let files = view.file_catalog().expect("catalog registered");
let origin = files.file_for_record("entries", "entry-47")?.unwrap();
let members = files.records_for_file(origin.file_id)?;
```

Use separate public constructors for retained input and rereadable input. The latter must require a registered reader/version or a checked file-range access capability at construction. This prevents accidentally discarding the only copy of searchable content. File and provider access handles belong to one index instance.

### 3.1 Fixed implementation decisions

| Decision | Implement this behavior |
|---|---|
| Registration and schema | Register collections, providers, and at most one optional `FileCatalog` before `IndexBuilder::build`. Freeze these declarations for the index lifetime. Keep the read-only schema and existing file-opening facade. Expose operations on owned input, file-linked input, and versioned provider input explicitly. The ordinary file import uses the existing scheduler and meets the same logical admission contract. |
| Segment layout | Use a closed internal enum with retained, file-range and provider-backed variants. Select it once per segment scan. Keep source-specific columns outside the common record header. Store retained values in immutable shared blocks; hold one registration handle per compatible segment. Use the current `SegmentPolicy` for sealing. |
| Reader contract | `RecordVersion(u64)` is an opaque provider-issued token scoped to its registration and record key. Supply `read_projected(key, expected_version, projection)` plus a default `read_batch` that preserves request order and returns one result per key. Distinguish changed version, unavailable source and fatal reader error. A provider must signal a stale token even when a newer body with the same ID is available. |
| Lookup and API errors | `file_for_record` uses the three outcomes in section 4. A known empty file returns an empty reverse iterator; an invalid or retired handle returns `FileNotFound` in that view. Retained records support logical reads; original byte requests without an authoritative byte representation yield `OriginalBytesUnavailable`. All record keys remain usable after a path-only move under the current identity rules. |
| Routing and memory | Reuse existing equivalent indexed routes. For a missing forward route, use a collection-scoped immutable base ID-to-address table plus copy-on-write delta shards, reusing the file catalog’s existing sharding convention. For missing reverse routing, index `FileId` to participating segment/slot lists. Reuse shared record ID storage. During compaction publish remapped addresses, reverse links and active masks in one root replacement. No scan of unrelated segments on a point lookup. |
| Producer lifecycle | `submit` returns after memory acceptance or a complete spool frame. `try_submit` is memory-only. When configured capacity is exhausted, return the input with a capacity error; `try_submit` returns `WouldBlock` for transient capacity/lock contention. Reject an empty batch and oversized batches before admission. Dropping a receipt never cancels the batch. `finish` drains; explicit cancellation cancels the unpublished suffix and wakes waiters. Dropping the last session owner closes new admission and drains the already accepted prefix. |
| Storage and installation | Default to 64 MiB pending resident input, 64 MiB maximum estimated input per batch and 4 GiB live spool. Create the temporary directory lazily on first overflow, with ≤64 MiB target per chunk; a single larger encoded frame gets a dedicated chunk subject to quota. Use the workspace’s bincode encoding with a fixed documented configuration, a format version, checked lengths and SHA-256 for each frame. Reclaim fully consumed chunks. No fsync or restart replay contract. Assign admission ordinals only after reservation and successful staging. Install through the existing lifecycle publisher; section 5 specifies failure handling. |
| Compatibility and escalation | Keep current file-backed constructors and serialized CLI field names. Migrate Rust call sites to optional provenance in this branch. If an acceptance gate or invariant cannot be met, report the reproducer, measurements and exact conflict. Only the user can approve a change to a contract or release threshold. |



### Where a residual scan gets its data

At ingestion each record has one authoritative read strategy. Implement these choices behind a segment-level access interface:

| Backing | At ingestion | On query |
|---|---|---|
| Retained typed records | Validate/index by reference, then move the typed record and any required adapter-owned text into immutable segment-owned storage. | Borrow the record or requested fields/text. A logical result is materialized only for requested winners. |
| File ranges | Index the adapter's decoded record and retain the checked file locator, source version and representation identity. Keep the existing raw/broken/unreadable file behavior. | Read grouped, revision-checked ranges using the existing bounded file access session. Decode the projection or use the existing exact borrowed scanner when eligible. |
| Application reader | Register a `Send + Sync` reader and submit the typed value plus a provider-issued immutable version token. Use the record key and token to address the original. | Call the registered reader with the requested keys, their expected versions and a projection. It returns logical values/text or a source-changed/unavailable outcome. Never silently evaluate current data under an older token. |

Give an external reader one required projected single-record read method and a default batched method that loops over it; optimized implementations may override the latter. Carry typed failure outcomes. Keep I/O out of lifecycle/publication locks. Pin reader registrations for the lifetime of a view. File-free users that only insert values need implement no reader. A fixture reader backed by a versioned in-memory map is sufficient to implement and prove this boundary. Actual XML/JSON-LD adapters are out of scope.

File provenance and payload backing are independent. An owned record can have a file association for navigation and continue to read from its retained value if the file changes. A file-range-backed record requires a catalog and a range valid for that file revision. For retained data, derive default searchable text from validated logical strings exactly as specified by the registration; if an adapter supplies different segments, preserve their paths, value boundaries and search representation for future exact scans. Do not build bigrams from one representation and verify against another.


## 4. File catalog and optional record provenance

Expose a read handle through `IndexView::file_catalog() -> Option<FileCatalogView<'_>>`. It must describe exactly the same publication as the view. Registering a catalog with zero files yields an empty service. An index created without the service returns `None`. The queue's temporary files, if any, are private implementation storage and never appear in the catalog.

| Pinned catalog operation | Contract |
|---|---|
| `file_for_record(collection, id)` | Resolve the active record and its optional association. Return `Result<Option<RecordFileInfo>, LookupError>`. Use `RecordNotFound` for an unknown key, `Ok(None)` for a live unlinked record and `Ok(Some(info))` for a live linked record. An association supplies a file handle and an optional half-open byte range. |
| `records_for_file(file_id)` | Iterate live record keys in every associated collection. Empty files are valid. Include all distinct records when multiple records occupy one file; overlapping provenance across collections is valid. Offer collection filtering without scanning unrelated records. |
| `file_by_path(path)` / `file(file_id)` | Reuse the catalog's normalized repo-relative path rules and stable file identity. Keep path, size, times, current version and diagnostics file-owned. Resolve a path once. Preserve current path ordering for callers using it. |

Keep one optional file link per record in this version. File-only provenance carries a file handle without an invented range. Range provenance requires a file, a checked range and the correct file version. Preserve the file reader's existing non-overlap/order rules for independently framed records within one input. They are separate from optional provenance. Reject supplied links when the registrar has no catalog capability. A record without a link remains valid.

Use existing per-segment ID maps and file-to-slot lists. The pinned view needs efficient routing in both directions: route a record key to its live address, and a file ID to only the participating segment/slot lists. Use existing suitable routes first. Where lookup currently walks every segment, add a compact shared routing index at the publication boundary, incrementally updating affected entries. Avoid indexing copied path strings per record, scanning the corpus for a reverse lookup, or cloning a global identity hash map for each accepted batch. Index size and lookup work are part of acceptance.

A catalog registration or link update participates in the same staged change as the records that refer to it. A batch can identify a newly declared file by a batch-local token before a global handle is published. Check path, range, size, expected revision and registration identity before installing links. Failed publication must not leak new path entries or dangling reverse links. Reuse the original file version and path normalization checks on the existing file ingestion route.

File-backed moves, replacements and deletes retain today's semantics, including existing distinctions between stable-ID moves and reindexing when identity depends on a path. Optional provenance attached to independently owned records grants no ownership to the file importer. A file move updates the displayed path through the catalog. Retirement of a file or replacement of the content invalidates revision-specific provenance on independently owned records, without deleting those records; clear obsolete links in both directions. Preserve a path-only association through content changes while the file identity remains active. Pinned older views keep their previous consistent mapping. A historical view opening physical bytes still performs the existing source-change check.

Represent public provenance using `RecordMetadata.file: Option<RecordFileInfo>` and `SearchHit.file: Option<RecordFileInfo>`. `RecordFileInfo` carries file identity, path, status/metadata and `Option<ByteRange>`. Resolve paths when inspecting a record or materializing winners. Public callers get an ergonomic record key and origin even in locator-only mode. Keep record class and logical diagnostics independent of file status. Migrate all uses of unconditional `hit.file_…` and byte fields. File-backed CLI/export/desktop outputs must preserve existing meaningful values and existing wire names. For unlinked records emit JSON null for existing file-specific output keys; for path-only links emit null for byte ranges. Preserve the existing container shape, record ID, class, generation and evidence. Never disable navigation by record ID just because the hit has no path. Never synthesize an empty path, file zero, a zero range or an epoch.

## 5. Producer queue, batching and publication

**Required behavior:** a producer can run ahead of indexing and segment sealing. Submission acknowledges ownership transfer. Searchability is acknowledged later. Use bounded resident buffering with temporary disk overflow by default. A producer can continue while index workers are paused, up to the configured storage capacity. Sustained input exceeding device throughput or all available capacity cannot be accepted indefinitely. Surface that condition explicitly and keep unaccepted data with the caller.

| Operation | Required semantics |
|---|---|
| `writer.batch()`, `insert`, `replace`, `delete` | Build an owned batch locally, amortizing per-record overhead. Track input weight once while forming the batch. Avoid a second full traversal or serialization under the queue lock. |
| `submit(batch) -> Result<Receipt, SubmitError<Batch>>` | Transfer the complete batch into a memory reservation or completed spool frame. Return without waiting for indexing, segment finalization or publication. The overflow path can spend time writing the input. Capacity/closed/pre-acceptance failures return the owned batch for retry. |
| `try_submit(batch)` | Memory-only nonblocking offer. If there is no immediately available in-memory admission, return `WouldBlock(batch)`. Never do disk I/O in this call. A successful offer receives the same ordering and receipt semantics as `submit`. |
| `Receipt::wait_published()` | Return the published revision or the specific terminal error. Every accepted receipt reaches a terminal state while the process is running. Receipt lifetime is independent of the submitting producer handle. |
| `flush()` / `finish()` | A barrier captures the accepted prefix at the call's linearization point. Wait until it is searchable or failed, including partial final segments. Later submissions do not prolong a flush. Finishing an ingestion session closes all its writer clones, drains the accepted prefix, and reports the result. Explicit cancellation wakes blocked waiters. |

**Ordering and atomicity.** Allow one active public ingestion session per index with any number of cloneable writers and registrations. Starting another session after finish or failure gives it a fresh identity. Reuse the active session from `index.ingestion()`; explicitly closing that session prevents reuse by stale writer clones. Use one ordered admission sequence per session. Cloneable producers may submit concurrently. Define the order for concurrent calls by successful admission; preserve each producer's successful sequential call order. A returned success means the complete input is in process-owned memory or a readable temporary frame. Assign no public holes for failed pre-admission writes. Expensive preparation and segment finalization can complete out of order. Publish only complete ordered batches. A batch spanning several segments becomes visible atomically; multiple complete batches may share one publication revision. Never allocate a permanent tiny segment per API call. Do not wait for a full segment to make progress when the queue is idle or a barrier is pending. Keep session finalization separate from shutting down searches on the index.

Stage validation and ID conflicts against the last committed state plus prior accepted changes in sequence. On a failed admitted batch, publish the successful prefix, leave the failed batch completely unpublished, fail its receipt and cancel later unpublished receipts with the originating sequence. A new ingestion session may resume against the last good view. Use the existing lifecycle publication coordinator for one serialized installation step. Revalidate every touched key, file version and source handle against the current root before installing prepared work. On a changed precondition return a typed conflict and apply the admitted-batch failure rule. Maintenance may retry its private work under the existing maintenance policy. Accepted data must never be installed twice. Internal retries must not reread mutable provider state without its version check.

**Resource policy.** Provide configurable pending resident bytes, spool bytes/directory and per-batch limit. Initial defaults are 64 MiB pending input in RAM and 4 GiB live temporary spool data. Permit `spool_bytes = 0` for strictly memory-only operation, including environments that allow no temporary files. Use a documented per-batch cap (initially 64 MiB of estimated owned input); return `BatchTooLarge` with ownership so the caller can split the batch. Track capacities, nested owned values and custom text sufficiently to avoid a tiny estimate for a huge record. Distinguish estimated heap bytes, encoded spool bytes, bounded in-flight worker work and final index memory in metrics. The 64 MiB pending budget is not an RSS guarantee.

- Use the existing bounded construction/segment scheduling machinery. Limit dispatched work and the out-of-order completion buffer, and prioritize the oldest ready ordinal. Cap resident waiting descriptors at 65,536 per session and store overflow bookkeeping sequentially in spool chunks. Reject admission before accepting ownership if neither the resident nor disk quota can cover it. Work waiting behind an early slow batch must not grow unbounded in RAM.
- Spool only owned input data, registration identifiers and versioned references. Keep Rust trait objects in the registration table. Use process-private temporary files outside the indexed tree by default, versioned length-delimited frames with checked sizes and corruption detection, and bounded chunk rotation/reclamation. Never publish from a partial frame. Clean up on normal shutdown, failure and cancellation; leave user files and directories untouched. This spool provides burst capacity during a run. A successful submission does not promise recovery after process termination.
- Avoid file creation, serialization and input cloning on the in-memory path. Avoid holding a queue/publication lock for disk writes, adapter callbacks or segment construction. Reserve budget before competing producers write, release it on all failure paths, and let readers see only fully committed frames. A full spool, permission error, disk-full write or shutdown must produce an explicit, testable result. Expose accepted/published counts, pending/high-water bytes, spool bytes, failure sequence and producer time spent in overflow writes.
- Keep existing file discovery/JSONL streaming fast. Expose revision-checked file jobs for the file registrar; workers perform framing and decoding. Keep the existing file-build scheduling entry point and route its decoded values into the shared logical admission/publication code. Avoid expanding ordinary JSON files into an owned record queue solely to feed them back into the parser. Preserve current file-level mutation atomicity; a multi-record file replacement cannot become visible half-retired.

## 6. Query execution and observable semantics

1. Preserve `proven ⊆ actual matches ⊆ possible ⊆ input` in each pinned slot domain. Carry existing proofs and restrictions through the planner, Boolean composition and paging. Verify only unresolved candidates/terms. Uncovered records in a partially indexed domain remain candidates. For `NOT`, absence of a candidate proof is insufficient evidence to reject or select a row. When no usable index exists, scan the live records in scope.
2. Dispatch reads by backing at a segment or candidate-group boundary. Project residual fields, text, and other data actually required for sorting/evidence/payload. The existing evaluator applies the same equality, range, type, missing/null, array, relation, regex and text rules. A pure match-all locator/count can enumerate live slots. An exact indexed count can run without payload access; evidence or requested payload can independently require a read.
3. Preserve borrowed JSON verification and combined text/filter scan in `source/verification.rs` and the existing conservative custom-reader fallbacks. Isolate their dispatch behind the reader/adapter boundary. A registrar name or extension string must never confer trusted JSON behavior. Expose representation/coverage and projection contracts to adapter authors. A generic external adapter can return typed values and text and rely on core verification. Keep optimizer internals private. Batch compatible file reads in source order and application reads per provider/version; check cancellation and limits and preserve output order independently of read order.
4. In fileless records `@record.id`, `@record.class` and collection metadata are available. `@file.*` is absent when no file is linked; byte-start/end/length are absent when no range exists. Use the ordinary missing-path semantics, including for state predicates. A linked file whose creation time is unknown retains the current file-backed null behavior. An unset repository root is absent. Apply the same rules in metadata planning, direct lookup, the reference evaluator, sort and evidence. A mixed-collection search must give the correct per-record answer.
5. `ReturnMode::Logical` reads the authoritative typed record. `ReturnMode::Bytes` requests original source bytes. Add `Payload::OriginalBytesUnavailable` for a live logical record lacking original source bytes. Keep I/O and stale-version failures on their existing diagnostic/error path. It is possible to have valid file provenance but no authoritative byte payload. Do not serialize a typed value to JSON to fabricate original bytes. Preserve existing raw fallback, broken-file, and unavailable-source diagnostics for real files.
6. Exercise ordinary and streaming search, pre-index/partially built views, verified-result cache, direct ID access, sorted/deep pages, relations/backlinks, reference evaluation and explain/analyze. Cache identity includes publication/registration, schema and text-representation versions as applicable. Metadata-only moves and updates must invalidate or correctly rebind cached locators. Streaming, limits and error reporting must work when there is no file group to drive progress.
