# Unified query planner and index capability results

Task: `unified-query-planner` · 11 November 2026. Starting master: `6ef66ec8f4bf15bfcaaf6cc4c7493bcf9bb592fc`. Implementation: `05c00a3cbfa2f218ed063681eccbd9769386aef5` on `master`. The implementation commit was pushed immediately; benchmark harness commit `00f501902c8aee2a66da5cb829b56ab89dbf0ac8` only exposes prepared-cache size. This report records the exact-revision acceptance comparison and the subsequent focused rechecks.

## Capability contract and flow

`PostingIndex` remains the authoritative storage for typed value, length, presence, null, and exact-empty-string facts. Its separate `value_complete`, `length_complete`, and `empty_string_complete` flags, `covered_records`, kind, multiplicity, and statistics are interpreted per bound expression. Automatically observed short strings carry an additional record-identity coverage bitmap; empty selections have their own bitmap. A named custom posting without a complete coverage guarantee cannot exclude records. These are capability and coverage facts, not producer priority. An observed numeric key does not change the bound type of a mixed field.

At publication and snapshot restore, `TextBindingCatalog` derives the canonical field-to-text-binding names once from the schema. On a query, `IndexCatalog` borrows the published declared, observed, and named postings plus raw, fallback, and field text indexes. It stores no copied posting, dictionary, or membership. Field lookup returns all applicable posting representations in constant time. A `PostingAccess` assesses compatibility, capability, completeness, cardinality, and lookup/residual cost, returning a prepared operation and physical identity. Estimation, execution, and EXPLAIN use that same proposal; execution resolves its identity only within the owning published revision. An exact operation supplies a proof; a candidate operation retains residual verification and its uncovered domain. Structural `must`/`may` composition remains sound under AND, OR, and NOT.

`PreparedFtsAccess` applies one shared text representation and coverage check to literal and regex FTS over full generations and incremental segments. It feeds both estimate-only and executing paths; bigrams remain candidate-only and field scope still requires field verification. Short/empty literals, unavailable grams, incomplete custom raw coverage, and incompatible matchers use the established residual route. The common text-binding lookup also serves FILTER text prefilters. No source freshness check or query-time indexing was added.

| Query surface or former decision | Current path |
| --- | --- |
| Declared vs inferred posting estimation and execution | One `IndexCatalog::field_postings` lookup and `PostingAccess::assess/execute`; `InferredPosting` and the separate inference query methods were removed. |
| Full-generation FILTER, count, pagination, sorted search, streaming, relation target filters, and EXPLAIN | Existing `PlanContext` selects common prepared posting accesses and preserves proof/residual behavior. |
| Incremental lifecycle segment FILTER and Boolean bounds | `segment_expr_bounds` assesses the same posting accesses over the segment's logical domain and composes `must`/`may`; retired/fallback domains remain separate. |
| Unscoped and field-scoped FTS, including relation target FTS | One `PreparedFtsAccess` resolves representation and coverage, then estimates or produces candidate sets. |
| Field text lookup across generation/segment, FILTER/FTS | One borrowed catalogue method with canonical binding names derived at publication/load. |
| Complete scalar posting sort alternative | `IndexCatalog::sortable_scalar` checks facts regardless of producer. The order-page shortcut requires a proven filter when FILTER is present; residual FILTER/FTS retain filter-first execution and verified-result reuse. |

Explicit indexing hints and opt-in automatic inference remain unchanged. Posting capability flags and source data continue to use their existing snapshot format; the text-binding map is derived at restore and is not serialized. Extension bindings retain their existing operation and coverage checks. The catalogue lifetime is bounded by its collection generation or segment, and prepared plan decisions carry only a physical identity/operation, not a borrowed pointer into a retired snapshot.

## Correctness and benchmark environment

`cargo test --workspace --locked` passed on the implementation commit, including 503 core tests and 158 desktop tests. `cargo clippy --workspace --all-targets --locked` passed with existing warnings. The new tests compare complete declared and observed postings with identical contents/capabilities, plan kind/exactness and results; they also cover the warm-cache sort regression described below. Existing core, lifecycle, snapshot, extension, streaming, relation, Boolean, and EXPLAIN tests passed. `git diff --check` passed.

The unchanged extended 194-query Musenalm suite ran against binaries built from exact commits `6ef66ec8` and `05c00a3c` on this computer, with the same absolute corpus root, four query workers, ASCII/Unicode, cache off and 64 MiB verified-result cache, and three timed repetitions. Both runs passed all **776 profile rows**. Total matches, returned counts, candidates, file opens, source bytes, parses, exact posting matches, scans, and residual evaluations match on every row. Q115–118 and Q120 retain zero source work under the structural posting capabilities. Index/snapshot byte estimates are identical: ASCII 69,662,968 / 129,139,458; Unicode 72,571,368 / 131,650,034. Build time was 2.597 → 2.600 s ASCII and 2.601 → 2.588 s Unicode. Peak RSS changed by +0.55% ASCII and −1.59% Unicode, below the 5% threshold. Raw CSVs, JSONL measurements, query plans, manifests, and build metrics are under [overnight benchmark results](../../../bench/results/unified-query-planner/overnight-2026-11-11/).

An initial uncommitted comparison found a real Q189 warm-cache regression: allowing a complete declared sort posting selected the posting-order page shortcut for a residual `preferred_title ~ 'Goethe'` FILTER, bypassing verified membership reuse. Warm source opens rose from 7 to 203 even though results were correct. Commit `05c00a3c` gates that shortcut on proven FILTER membership; the new focused test checks cache reuse, and the exact-revision full suite has identical Q189 counters to the baseline. The initial run is retained as preliminary evidence in `final-suite`; `matched-suite` is the acceptance run.

## Timing rechecks and planning measurements

The three-sample full suite flagged 77 case/profile timing rows above both 5% and 0.5 ms (76 cache-off, one Q190 warm). We first repeated the 76 cache-off cases with seven samples in alternating baseline/final/final/baseline order. All 152 case/profile rows retained identical result and work counters, and 22 rows still crossed both thresholds in both pairs. A second alternating run of those 17 distinct cases used 21 samples and narrowed the repeatable flags to Q072, Q116, and Q136 in ASCII cache-off, again with identical work. The focused source-free Q116 run (21 samples) measured 11.42/11.20 ms baseline and 10.86/11.27 ms final; it did not reproduce the mixed-suite 18.9/22.5 ms final values. Q072 in isolation measured 6.06/6.16 ms baseline and 6.13/6.25 ms final. Q136 in isolation measured 81.39/81.75 ms baseline and 93.77/85.18 ms final for ASCII; the second final round was only 4.2% above its paired baseline. Unicode Q136 alternated in the opposite direction. These timing reversals and the 2.5–4.2 system load on the shared desktop support CPU/OS-cache contention as the cause of the mixed-run outliers; no candidate, index, source, parse, or residual work changed. Q190 warm recheck (21 samples) measured 90.03/85.06 ms baseline and 90.68/88.02 ms final for ASCII, and 87.27/87.43 ms baseline and 89.55/88.72 ms final for Unicode; no pair exceeded 5%. Raw seven- and 21-sample runs are retained with the full suite. The earlier Q189 source-work regression was an implementation mistake and was corrected before the acceptance runs.

The focused planning comparison used the identical patched harness source with `--release --locked` on baseline `6ef66ec8` and current `00f50190`, ten cases, ASCII/Unicode, seven repetitions, four workers, and verified-result cache disabled. All 20 case/profile rows passed, with every reported result and work counter identical in both cache settings. The prepared cache was measured at 0 and 16 MiB; it recorded 0 versus usually 6 of 7 prepared-plan hits. Planning still executes for a prepared query, so a cache hit does not eliminate the planner's measured work. Representative ASCII planning medians (ms) with the prepared cache disabled:

The prepared-cache-on run also passed all rows; for example Q056 planning was 0.642 → 0.648 ms and Q141 was 1.092 → 1.137 ms. Q190 planning appeared 13–30% higher in one seven-sample comparison; a separate alternating 21-sample, prepared-cache-off recheck gave 0.583/0.643 ms baseline and 0.595/0.598 ms final for ASCII, and 0.675/0.661 ms baseline and 0.583/0.617 ms final for Unicode. Its planning increase did not repeat. The diagnostic plan counters were 33 dictionary visits and one bitmap build in both revisions.

Musenalm is a full-generation corpus and supplies no controlled partial-coverage or incremental-segment planning timing case. Existing partial-coverage, lifecycle, snapshot, and segment tests passed, and the new declared/observed parity fixture checks the common physical access without source reads. The harness does not expose per-query allocation counts; no allocation claim is made. The published index/snapshot byte totals and build RSS above give the available retained-memory check. Remaining limitations are representation/coverage facts: partial scalar dictionaries cannot prove absence outside their covered selections, and raw bigrams can only restrict field matches that still need verification. No repeatable implementation-caused regression remains in the measured acceptance set.
