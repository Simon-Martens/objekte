# Direct snapshot access validation inventory

Task: `direct-snapshot-access`. This inventory distinguishes lookup reconstruction from work that still validates external bytes in the combined implementation at `84bd746cff`.

| Layer and invariant | Bytes read | When and traversal | Allocation / lookup reconstruction |
| --- | --- | --- | --- |
| Managed generation manifest: version, model, configuration, segment identities, active masks, and validator stamps | Manifest bytes and recorded checksums | Before generation restoration; full small manifest parse | Decoded manifest metadata and active bitmaps; no source discovery |
| Segment envelope: magic, version, directory order, extents, overlap, required sections | 24-byte header and 56 bytes per section, plus directory entries | On segment reader construction; one small directory pass and extent sort | Section map and directory span vector; no record or dictionary lookup table |
| Segment section SHA-256 | Entire section on its first `SegmentReader.section` access | Once per immutable reader, with `OnceLock`; the mapped mode still touches every byte in that section | Digest state only; `PostingPayloads` is intentionally excluded from eager whole-section checking |
| Dictionary routing and leaf structure | Bigram and scalar dictionary sections; each leaf's offsets and descriptors | At dictionary open. Untrusted path checks typed order and cross-block fences; stamped path still checks leaf framing. Both visit the leaves once. | Small block directories and per-entry posting validation slots; no materialized posting map |
| Gram filter structure and dictionary binding | `GramFilters` section and each filter header | At open; the section SHA touches all filter bytes. The checked reader borrows bit words. | No filter construction from dictionary entries; no additional dictionary visit |
| Gram filter semantic coverage | Each gram dictionary key and corresponding filter bits | In the **existing untrusted dictionary validation pass**; current validator stamp reuses the prior proof. Constructed readers use writer proof. | No reconstructed filter or additional pass |
| Posting payload checksum, cardinality, and eligible domain | Referenced Roaring payload block only | On first use of each descriptor; checked result may be retained in a bounded cache | Bounded cache, not an opening scan |
| Record-slot header, extents, domains | `RecordSlots` header, fixed rows, arena bounds, serialized Roaring domains | Checked before publication; validates offsets and domain coverage | Two decoded Roaring domains and small layout descriptors; no classification-derived bitmap |
| File membership, metadata reference, source range, fallback identity | Each 40-byte file row, 4-byte membership, 36-byte record row, referenced catalog metadata and record ID bytes | One membership traversal before publication, then a sequential record-row pass to check ID-arena gap/overlap; checks sorted file IDs, unique paths, exact membership coverage, revision and collection agreement, diagnostic references, ranges and domain consistency | One `Vec<bool>` of record coverage, temporary path set and one `FileEntry` per file; no installed file map or membership lists |
| Segment ID order and relation structure | Persisted identity order and relation section | Checked against record slots and relation declarations before publication | Identity-order vector remains resident for existing relation/sort APIs; exact ID lookup reads this sorted order and borrowed record IDs |
| Catalog slots, paths, historical references, versions | Full catalog bytes, slot/history/native/query tables and metadata arena | Manifest digest once, then sequential validation of the slot, historical, native-path and query-path tables before publication; checks holes, offsets, IDs, comparator orders, unique coverage, native/query spelling agreement, history and references | Temporary historical byte-reference map and Roaring coverage bitmaps; no installed current/historical `FileEntry` table, path hash map, path sort, or path tree |
| Cross-segment live IDs and revisions | Active identities in each segment's persisted order, catalog revision and membership fields | Streaming heap merge before publication; one traversal of live IDs to reject duplicate IDs or mismatched current revisions | One pending owned ID per segment plus heap and cursors; no repository-sized cloned-ID set |
| Sort, relation, inference metadata | Referenced sort/relation/inference sections | Bounded eager decoding and structural validation at open | Some owned leaf structures remain for current sort/relation APIs; see performance report |

The catalog and record-table validation passes remain linear in persisted metadata size. The section hashes touch their entire checked sections, even in mapped mode. Metadata installation does not recreate the validated lookup tables, and a normal query/update has no delayed full reconstruction. A checksum detects byte changes but does not prove ordering, table coverage, domain agreement, or identity uniqueness. A matching validator stamp can reuse the earlier semantic proof for selected immutable sections; the mutable generation/catalog checks still run before publication.
