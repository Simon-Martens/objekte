# Remove prepared-query binding cache: results

Task `remove-binding-cache` on `integration/remove-binding-cache`, worktree `/home/simon/source/objekte-integration-remove-binding-cache`. Base is `0c63651458` from `integration/direct-snapshot-access`; the ordinary release baseline binary was built from `8747efc47e`, whose later changes through `0c63651458` affect only diagnostics and documents. Implementation commit `1e22afd17b`; feature-gated timing instrumentation and runners `edb1e753db`. Executable hashes, exact commands, and [raw samples](../../../bench/results/remove-binding-cache/final-20261114/README.md) are archived.

The repository-owned `PreparedCache` LRU, its mutex and bincode key, `RepositoryOptions.prepared_cache_bytes`, `WorkCounters.prepared_plan_hit`, retained-size charging helpers, and benchmark flag, manifest field and hit columns are removed. `prepare` still binds each selected collection's filters and FTS and tracks parameter types, fresh on every request. Verified-result and internal decoded-posting caches remain. Verified cached result materialization no longer performs a binding solely to count a hit. A prepared binding already available in inferred-order and explanation paths is reused within that request. Removing the public `RepositoryOptions.prepared_cache_bytes` field is an intentional breaking API change in this pre-1.0 repository.

## Correctness and timing

`cargo test --workspace --locked` passed on the combined branch. `cargo clippy --workspace --all-targets --locked` passed with existing repository warnings. `cargo fmt --all -- --check` and `python3 scripts/format-rust-spacing.py --check` both failed on broad pre-existing formatting drift, starting in untouched `crates/cli/src/execution.rs`; no global reformat was committed. A new test verifies that each bind compiles new regexes for two collections and has independent bound state. An archived counter JSON with the retired key still deserializes, while new serialization omits it. In-repo callers compile without the removed option. The full benchmark matched every result digest, count, return count, and order/evidence digest in memory and on-demand modes. The focused regex cases Q163, Q164, Q173, Q182 and Q186 all passed.

| --- | ---: | ---: | ---: |
| Memory | 0.985 | 0.949 | 1.029 |
| On-demand | 1.021 | 0.959 | 0.979 |

These ratios mix short queries and broad scans; individual regex medians vary in both directions. The on-demand median geometric mean is 2.1% slower, while its p95 geometric mean and aggregate case time improved. This is consistent with a small fresh-binding cost and normal run noise, rather than a broad query regression. The raw CSVs show all cases.

Feature-gated `OBJEKTE_BIND_PHASES=1` tracing measured each `prepare` call in full benchmark runs, including separate diagnostic/explanation calls outside the latency samples. The current standard manifest contains 150 cases; the reviewed 194-case dirty measurement in the task specification is a historical checkpoint, not the current manifest. With five repetitions in both ASCII and Unicode, the 150-case run had 2,400 binding calls, 6.628 ms total, mean 2.762 µs, median 1.232 µs, p95 9.952 µs, maximum 38.651 µs. The extended 220-case run had 3,520 calls, 13.553 ms total, mean 3.850 µs, median 1.398 µs, p95 12.535 µs, maximum 146.219 µs. Of those, 80 regex calls took 3.314 ms total, mean 41.422 µs, median 39.424 µs, p95 80.781 µs, maximum 146.219 µs. The previous dirty-release 220-query figure in the specification was 1.438 ms total, 6.54 µs mean and 204 µs maximum; different instrumentation and call counts prevent a direct ratio. The current trace confirms regex compilation is the tail.

Peak process RSS in the memory campaign was 1,086,956 KiB baseline versus 1,069,396 KiB candidate (about 17 MiB lower); on-demand peak RSS was 322,420 versus 342,456 KiB (about 20 MiB higher). These single process peaks are sensitive to allocator and OS state and do not establish a retained 16 MiB saving. Open/build fields in the campaign vary across the two fresh processes: ASCII on-demand managed open was 276.6 versus 287.1 ms and Unicode 267.4 versus 264.0 ms; the implementation has no change to build or restore code. Three paired initial ASCII flush medians were 323.617 versus 352.453 ms, with identical 141,616,861-byte stores; unchanged flushes were about 1 µs. The small flush sample is noisy and the cache is not used by the flush path. No source reads occurred on measured managed opens.

The removed counter and option are absent from current benchmark manifests and diagnostic JSON. Archived `bench/results/**` and historical `docs/ai/done/**` were left unchanged. A separate regex-only cache is not recommended now: the worst measured fresh bind was 146 µs and the full campaign showed no material repeated-query regression. If a future workload repeatedly issues regex bindings at high rate, the archived per-case results provide a baseline for that separate decision.
