# In-memory index

Source JSON files define the repository. `Repository::open` discovers populated JSON folders without a manifest; optional schema bases group their descendant folders into one collection. See [collections.md](collections.md) for ownership and code APIs. `Repository::load_repository` still supports the older manifest and falls back to discovery when no manifest exists. `Options::new()` selects `CacheMode::Memory` and `BigramEncoding::Ascii`; `CacheMode::Disabled` makes views scan source files directly. The in-memory picker serves views and default JSON filters. Its bigram filter can be saved to `.objekte/.cache`; an existing saved filter is loaded and refreshed automatically.

`BigramEncoding::Ascii` indexes printable ASCII byte pairs as before. `BigramEncoding::Utf8Bytes` indexes consecutive UTF-8 **byte** pairs, including bytes inside and across Unicode scalar encodings. These are not Unicode code-point bigrams. Set `Options.bigram_encoding` or pass `--bigram-encoding utf8_bytes` to use it for schema-free collections. A collection schema can override the runtime setting with `"x-objekte": { ..., "bigram_encoding": "utf8_bytes" }`. Resolution is collection override, runtime option, then ASCII. The mode is explicit; text language never selects it. ASCII letters are lowercased in either index, while non-ASCII bytes are preserved. Values also contribute a separate Unicode case-folded projection where needed; case-insensitive matching uses only safe posting constraints and still verifies source text. Control-byte pairs and scalar separators are not used as required postings. UTF-8 mode has a 128 KiB lookup table and allocates posting columns only for observed byte pairs, so its build memory and saved size can exceed ASCII mode on multilingual data.

`bigram/` contains the local FFF-derived content-fed builder, compressed filter, and changed-file overlay, with the upstream tests and MIT license. `file_picker/mod.rs` owns the stable file table and construction; `file_picker/refresh.rs`, `rebuild.rs`, and `candidates.rs` own live edits, immutable reconstruction, and candidate selection. Smaller modules own typed postings, presence bits, sort orders, a general rendered full-text filter, and per-field normal/rendered filters. `text/` traverses every JSON leaf and applies schema rendering and exclusion rules. `json_filter/` owns filter syntax and evaluation. `repository/json_query/` separates in-memory, direct-source, and sorted execution; `repository/text_query/` separates matching and sorted execution from the main full-text verifier. `view_definition.rs` loads and executes independent named views. `repository/views.rs` retains the older collection-view API for legacy repositories. See [the core code map](code-map.md) for the query flow and test locations.

On a fresh index build, the source inventory enumerates and sorts IDs without reading metadata for every file. Rayon scan workers securely open each file, take its initial metadata stamp from the descriptor, read it, verify the stamp again, and store it in the final slot. Checked snapshot reconciliation still collects independent inventory stamps; rebuilds of existing slots still compare reads with their stored expected stamps. A fresh build can therefore accept an in-place edit that completes after ID enumeration but before that file is opened; edits during reading are rejected by the before/after check. Directory identity and membership checks and no-follow opening remain active.

`sorting/parser.rs` compiles `SORT BY` clauses; `sorting.rs` generates ICU4X secondary-strength
collation keys for strings. Case differences compare equal, accent differences
remain significant, and collection/ID resolves ties. `file_picker/sort_index.rs`
stores schema-declared single and composite orders. Single-field descending
order is derived from its ascending index while preserving ID order within
equal values. With a verified matching sort index, JSON and full-text queries
visit candidates in index order and emit the accessible page directly. They
stop after the batch containing a match beyond the repository cap, which
determines truncation.
When no matching index is usable, `sorting/buffer.rs` maintains only the best
accessible prefix and publishes provisional page replacements. Its JSON path
reuses parsed matches and validates only retained records. The secondary
snapshot contains sort keys and orders, bound to the schema root language and
pinned collation version.

Default JSON and full-text queries visit each collection's matching files by
modification time, newest first, with byte-sorted ID breaking ties.
`file_picker/modified_order.rs` stores that order as 32-bit references to stable
file slots. On an edit, it marks the old order position as superseded and puts
the same slot into a small ordered overlay. Searches merge both parts without
moving bigram postings. Larger overlays are compacted into a new order. The
order is saved in the `.secondary` cache; existing older secondary caches are
rebuilt once when opened.

## Index lifecycle

The picker enumerates JSON files within a collection boundary, stores relative IDs in a byte arena with stable slots, and builds consecutive and skip-one bigram postings over decoded scalar values and distinct Unicode-folded projections. One Sonic JSON tree supplies the text projection and field-presence bits. Top-level scalar fields marked `"index": true` enter typed B-tree postings and are omitted from the general normal filter. Every explicitly declared `x-full-text` leaf has its own normal and rendered bigram filters; its decoded value is also omitted from the general normal filter. A combined rendered filter supports unrestricted full-text queries. Standalone full-text candidate planning searches distinct B-tree keys for indexed scalar fields and unions matching slots with bigram candidates before source verification. Invalid container values remain in the general bigram projection so they can still be found. Declared sort indexes also project locale-aware keys from the source JSON; their collation keys cannot provide substring matching, so sort-only fields remain in the bigram projections. Typed postings use per-field `BTreeMap` keys for numbers, booleans, strings, explicit null, and a separate missing-field key. Missing means a valid JSON record omits that field; malformed JSON has no typed postings, but its raw and best-effort JSON-unescaped text enters the general bigram postings for standalone word and regex search. Malformed JSON has no JSON paths but can match source metadata predicates such as `@status = "incorrect_json"`. Missing never matches a JSON comparison, including `!=`. Indexed views select a page from ordered keys, then read the page files. Other views scan candidates and sort in memory.

The picker builds lazily per collection. `refresh(collection)` applies external edits, deletes, and additions. Changed files update ordered view keys and revision timestamps. Typed postings, runtime path postings, and presence bits are patched in place, as a database updates its indexes: the file moves from its previous keys, kept per slot, to its new ones. The compressed bigram filter is not patched; a changed file's new byte pairs are kept beside it and checked per file until a rebuild. More than 1/32 of a collection (at least 512 files) in that overlay triggers a rebuild. Removed IDs leave revision tombstones in the handle.

Registered value extractors can add named typed postings to that same B-tree. Their internal paths carry the descriptor and bound schema identity and cannot collide with JSON fields. The fused rebuild projection and refresh compute active derived values from the same Sonic parse; untouched collections do no extractor work. A refresh removes old derived keys from retained slot state before inserting newly extracted values. The direct derived query evaluates the public extractor against logical record access; the indexed query walks the posting keys and caches complete ordered slot lists separately from source records. Both materialize and check returned page records. [Library extensions](library-extensions.md) specifies the public grammar, null/missing and sort contracts.

The first build loads the sorted source inventory directly into final ID slots. Rebuild reuses those slots when their order is still compact; additions and deletions trigger compaction so the next immutable index has dense, ID-ordered slots.

A long-lived UI can call `warm_bigram_index(collection)` or `warm_all_bigram_indexes()` after startup. These build missing indexes without a query. `rebuild_bigram_index(collection)` and `rebuild_all_bigram_indexes()` refresh source inventory and rebuild bigram and scalar indexes. Rebuilding an existing picker retains in-process revisions and deletion tombstones. The all-collection methods run in name order and return per-collection metrics. Use a background thread, or call the collection methods individually to report progress between collections.

## Bigram snapshots

`objekte REPOSITORY cache save [--collection NAME]` writes compressed bigram snapshots below `.objekte/.cache`. `cache reindex [--collection NAME]` reads every source record again, rebuilds the in-memory indexes, and replaces those snapshots. In the TUI, Alt+S saves all collections and Alt+R reindexes and saves all collections in a background worker. The matching core APIs are `Repository::save_bigram_cache`, `save_all_bigram_caches`, `reindex_bigram_cache`, and `reindex_all_bigram_caches`. `Repository::save_bigram_snapshot(collection, path)` still supports an explicitly chosen path.

Each snapshot stores the base compressed filter with its ordered slot manifest. New `OBJSNP05` manifests store IDs in one byte arena, numeric nanosecond timestamps, and compact filesystem identities. The manifest records `bigram_encoding` and whether indexed scalar fields were omitted from the general bigram filter. Its `OBJBG002` filter and any skip-one index record the same encoding. Readers still accept `OBJSNP01` and `OBJSNP02` as legacy ASCII, as well as `OBJSNP03` and `OBJSNP04` with their recorded encoding. `OBJBG001` filters remain readable as ASCII. The snapshot records the Git commit at its source directory when saved, if one exists. Changed slots and their bigram sets are stored separately from the base filter. A companion `.secondary` file stores typed and field-presence postings, ordered view keys, modification-time slot order, key summaries, and any active full-text index. Its checksum binds it to the bigram snapshot, and its configuration fingerprint includes the effective encoding. A base whose scalar fields were omitted from bigram postings is rebuilt if that companion is missing or incompatible.

`BigramSnapshot::load_checked(path, source_root, recursive)` restores the filter and compares every manifest entry with the current source inventory and Git commit. It rejects missing, added, or changed files and incompatible or damaged snapshot bytes. `candidate_files(pattern)` resolves matching filter slots back to filenames; callers still verify matches against source JSON. The binary filter includes dense and sparse columns and the skip-one sub-index. The format is versioned and uses a checksum; writing replaces the snapshot atomically.

On first index use, a repository automatically loads an available snapshot when its source scope, encoding, and file IDs match. The early restoration path moves the validated ID arena into the picker directly; a background inventory later checks filesystem metadata without reading unchanged record content. Changed files are projected into the saved overlay and both cache files are replaced automatically. Added or removed IDs change the slot table, so the picker rebuilds and replaces the cache. A different encoding or an incompatible or corrupt cache triggers a rebuild; the early unchecked restoration path also rejects a mode mismatch before publishing the index. Global rendered and per-field normal/rendered filters are checked against the same mode. The current secondary layout uses `OBJSEC06`; older companions are cache misses. Collections with declared FTS fields rebuild the base filter when that companion is missing, because their values are separated from it. A Git commit change alone does not rewrite unchanged indexes; the stored commit identifies the revision at save time. `BigramSnapshot::load_checked` remains available for standalone use when every source stamp and Git commit must match exactly.

On TUI startup, an available bigram snapshot is published before checking source file metadata. Searches are available while a background worker inventories the collection; they verify candidate files against current source content and may temporarily miss new matches or show stale counts. The TUI shows `Checking files in background · search available` during this period. Each completed collection inventory patches changed, added, and deleted files into the live picker, saves a changed cache, and reruns the active search. The ordinary core index opening path still completes its source inventory before returning. `bigram_snapshot_loads` and `secondary_snapshot_loads` in warm metrics distinguish a restored filter from a restored companion index. The companion contains typed postings, field-presence bits, ordered view keys, key summaries, and optional rendered full-text postings; a collection with no declared fields can use its saved bigram filter without loading that companion.

When a schema declares any `x-full-text` field, including plain text, the picker builds its normal and rendered field filters alongside the general and combined rendered filters in one source pass. Markup or `exclude_fts` also activates the combined rendered filter. Schema-free collections continue using the general normal filter for standalone word and regex candidates. `warm_text_index` and `rebuild_text_index` act on collections requiring these filters. See [full-text.md](full-text.md) for field formats, matching modes, and source verification.

`build_posting(collection, path)` and `build_posting_all(path)` build or replace one runtime ordered posting for a JSON path. They read current source files, record scalar values plus separate null and missing keys, and retain path presence. The posting can answer `missing(path)`, `exists(path)`, safe scalar comparisons, and existential comparisons over complete repeated values. Ordinary scalar queries still report cardinality errors when a path yields multiple values. Full picker rebuilds rebuild runtime path postings after slot compaction. Source refreshes patch them like typed postings; a path can only become less safe, such as losing scalar safety, until the next rebuild. `infer_and_auto_index` rescans JSON on request, reports nested field shapes and semantic hints, and builds postings for inferred booleans, numbers, and bounded low-cardinality strings. Saved root `x-index-paths` rules are loaded in one batched source pass after the normal picker build. See [inference.md](inference.md).

## Reporting source changes

Objekte does not watch the filesystem. Opening a collection from a saved cache reconciles it with the source files; after that, changes reach the index only when the application reports them. Both entry points update bigram overlays, typed and presence postings, sort keys, the default modification order, record revisions and tombstones, the verified-query cache, and observed reference edges. When anything changed and the collection has a disk cache, that cache is rewritten.

- `Repository::diff(collection)` and `diff_all()` compare the source inventory with the index and return the created, changed, and deleted record IDs. Moves appear as a deletion and a creation. Without an index in the handle, `diff` restores a saved disk cache and diffs it, so the first call after startup lists everything changed since the cache was saved. `objekte REPOSITORY cache diff [--collection NAME]` prints the same report.
- `Repository::apply_source_changes(&[SourceChange])` takes the files the application created, changed, deleted, or moved, as paths that are absolute or relative to the repository root. It resolves every path to its collection and ID before changing anything, so one invalid path rejects the whole batch. It then rereads only those files, without enumerating directories. Each file is checked against its current state on disk: the report lists what actually changed, so a file reported as changed but already removed is deleted. A move may cross collections. Collections without an index in the handle are skipped, apart from dropping observed reference edges; their next load reconciles any disk cache.

Both return a `CollectionChanges` per collection: the `created`, `changed`, and `deleted` IDs, whether the collection was `indexed`, and the rewritten `saved_cache` path. Rewriting a large cache costs as much as `cache save`, so batch frequent edits where possible.

## Query reads

The default `auto` backend and explicit `bigram` backend select candidates through the picker. Safe typed comparisons and fields required by every matching branch narrow candidates; typed `OR` branches are unioned only when every branch has a safe indexed set. Selective bitsets enumerate set slots; default search orders them by modification time, including changed files, while dense bitsets walk a saved modification-time slot order. Covered top-level scalar equality, inequality, and range predicates and `exists` can get exact match sets directly from typed and presence indexes. Counted queries use the current index snapshot without checking every matching source file; only returned page records are read, parsed, and validated. This exact path falls back to source scanning for unsupported expressions or array-cardinality risk; changed files are patched into the postings it uses. `direct` evaluates source files without an index. `grep` uses ripgrep over source files as a candidate prefilter. These remain useful for parity checks and query shapes that need a broad scan.

`query_json_stream` emits validated page records through a callback in collection and modification-time order, with ID breaking timestamp ties. Bounded candidate batches may run in parallel, then publish in order. The final summary confirms the total and metadata; a later error invalidates provisional records. The CLI's `--output events` writes the corresponding JSON lines.

The older collection-view API uses ordered view keys for explicitly indexed scalar fields, including bytewise string order. Native JSON and full-text query sorting uses ICU collation for strings and string enums. Null, missing, and invalid-type positions retain their documented order. Independent named views use native query arguments.

Schema validation runs for returned JSON query matches, in-memory view pages, and explicit validation commands only when a collection has a schema. A parseable `get_record` response remains `pending` until validated, or reports `no_schema` if no schema is attached. Schema-free views default to `@id`. No validation state or reference edge is stored in the index. Outgoing references are extracted from schema-declared paths in requested records; incoming references include previously observed edges unless complete coverage is requested, which scans referring source collections.

## Freshness

`metadata-on-open` builds or checks a collection on first use of a handle. `metadata-on-request` repeats source metadata checks before a cache lookup. `hash-on-request` rebuilds the picker on each request and bypasses the verified-query cache. `refresh` explicitly reconciles one collection. Under an on-open policy, call `refresh` after an external edit to make it visible to index selection. A changed page file read before refresh can produce `Unstable` rather than a stale result. Indexed JSON candidates are compared with their stored stamp before reading and with their byte size after it; only returned or retained records get a second metadata check. A same-size edit completed during a candidate's read can therefore affect that request's count, but never a returned record.

The repository-local verified-query cache defaults to a 64 MiB budget (`Options::query_cache_bytes`; zero disables it). It holds bound query expressions, evaluated and matching slot bitsets, and ordered slot lists for complete results or proven leading prefixes. It holds no source bytes, JSON values, or rendered text. A complete match set can be reused with another indexed order, and a complete ordered list serves later pages by slicing its slots. Returned records are always read and checked from their source files. Safe conjuncts and disjuncts can reuse earlier verified terms; expressions with scalar-cardinality risk or source metadata predicates follow the regular path. Ordinary streaming APIs retain full candidate verification by default, including detection of a source changed late in a search. The TUI sets `Options::stream_query_cache` to reuse verified entries while still emitting provisional rows in order. This opts its streaming queries into the same `metadata-on-open` freshness limit as collected queries: non-page files are checked again when the collection is reconciled. Cancellation during verification does not publish partial entries. Changed collections, rebuilt indexes, and explicit configuration reloads invalidate affected entries. A lookup performs no filesystem check of its own. `metadata-on-request` refreshes before reuse.
