# In-memory index

Source JSON files define the repository. `Repository::open` discovers populated JSON folders without a manifest; optional schema bases group their descendant folders into one collection. See [collections.md](collections.md) for ownership and code APIs. `Repository::load_repository` still supports the older manifest and falls back to discovery when no manifest exists. `Options::new()` selects `CacheMode::Memory`; `CacheMode::Disabled` makes views scan source files directly. The in-memory picker serves views and default JSON filters. Its bigram filter can be saved to `.objekte/.cache`; an existing saved filter is loaded and refreshed automatically.

`bigram/` contains the local FFF-derived content-fed builder, compressed filter, and changed-file overlay, with the upstream tests and MIT license. `file_picker/` owns source inventory, bigram planning, typed postings, field-presence bits, revisions, and ordered view keys. `file_picker/text.rs` owns the separate rendered and raw full-text indexes; `text/` traverses every JSON leaf and applies schema rendering and exclusion rules. `json_filter/` owns filter syntax and evaluation. `repository/json_query/` contains the in-memory and direct-source query paths; `repository/text_query.rs` handles full-text verification; `view_definition.rs` loads and executes independent named views. `repository/views.rs` retains the older collection-view API for legacy repositories. Tests live in separate files under `crates/core/tests/`, `crates/cli/tests/`, and `crates/cli/src/tui/*.test.rs`.

## Index lifecycle

The picker enumerates JSON files within a collection boundary, stores relative IDs in a byte arena with stable slots, and builds consecutive and skip-one bigram postings over decoded scalar values and distinct Unicode-folded projections. One Sonic JSON tree supplies the text projection and field-presence bits; only top-level scalar fields marked `"index": true` are converted for typed postings and ordered view keys. It no longer copies the full tree into a second JSON representation during index construction. Typed postings use per-field `BTreeMap` keys for numbers, booleans, strings, explicit null, and a separate missing-field key. Missing means a valid JSON record omits that field; malformed JSON has no typed postings, but its raw and best-effort JSON-unescaped text enters the bigram postings for standalone word and regex search. Malformed JSON cannot match a field-based filter. Missing never matches a JSON comparison, including `!=`. Indexed views select a page from ordered keys, then read the page files. Other views scan candidates and sort in memory.

The picker builds lazily per collection. `refresh(collection)` applies external edits, deletes, and additions. Changed files update ordered view keys and revision timestamps; a conservative overlay keeps bigram and typed filtering complete until rebuild. Removed IDs leave revision tombstones in the handle.

The first build loads the sorted source inventory directly into final ID slots. Rebuild reuses those slots when their order is still compact; additions and deletions trigger compaction so the next immutable index has dense, ID-ordered slots.

A long-lived UI can call `warm_bigram_index(collection)` or `warm_all_bigram_indexes()` after startup. These build missing indexes without a query. `rebuild_bigram_index(collection)` and `rebuild_all_bigram_indexes()` refresh source inventory and rebuild bigram and scalar indexes. Rebuilding an existing picker retains in-process revisions and deletion tombstones. The all-collection methods run in name order and return per-collection metrics. Use a background thread, or call the collection methods individually to report progress between collections.

## Bigram snapshots

`objekte REPOSITORY cache save [--collection NAME]` writes compressed bigram snapshots below `.objekte/.cache`. `cache reindex [--collection NAME]` reads every source record again, rebuilds the in-memory indexes, and replaces those snapshots. In the TUI, Alt+S saves all collections and Alt+R reindexes and saves all collections in a background worker. The matching core APIs are `Repository::save_bigram_cache`, `save_all_bigram_caches`, `reindex_bigram_cache`, and `reindex_all_bigram_caches`. `Repository::save_bigram_snapshot(collection, path)` still supports an explicitly chosen path.

Each snapshot stores the base compressed filter with its ordered slot manifest. Each manifest entry provides the record ID, relative JSON filename, byte size, nanosecond modification time, and filesystem identity. The current `OBJSNP02` format stores a compact binary manifest and derives the filename from the ID on load; readers also accept the older JSON manifest in `OBJSNP01`. The snapshot records the Git commit at its source directory when saved, if one exists. Changed slots and their bigram sets are stored separately from the base filter. A companion `.secondary` file stores typed and field-presence postings, ordered view keys, key summaries, and any active full-text index. Its checksum binds it to the bigram snapshot and its configuration fingerprint prevents use after index or schema changes.

`BigramSnapshot::load_checked(path, source_root, recursive)` restores the filter and compares every manifest entry with the current source inventory and Git commit. It rejects missing, added, or changed files and incompatible or damaged snapshot bytes. `candidate_files(pattern)` resolves matching filter slots back to filenames; callers still verify matches against source JSON. The binary filter includes dense and sparse columns and the skip-one sub-index. The format is versioned and uses a checksum; writing replaces the snapshot atomically.

On first index use, a repository automatically loads an available snapshot when its source scope and file IDs match. It inventories filenames and filesystem metadata, without reading unchanged record content. Changed files are projected into the saved overlay and both cache files are replaced automatically. Added or removed IDs change the slot table, so the picker rebuilds and replaces the cache. An incompatible or corrupt cache falls back to a rebuild. Existing bigram snapshots without a companion secondary file are upgraded by building the other indexes once and saving the secondary file. A Git commit change alone does not rewrite unchanged indexes; the stored commit identifies the revision at save time. `BigramSnapshot::load_checked` remains available for standalone use when every source stamp and Git commit must match exactly.
On TUI startup, an available bigram snapshot is published before checking source file metadata. Searches are available while a background worker inventories the collection; they verify candidate files against current source content and may temporarily miss new matches or show stale counts. The TUI shows `Checking files in background · search available` during this period. Each completed collection inventory patches changed, added, and deleted files into the live picker, saves a changed cache, and reruns the active search. The ordinary core index opening path still completes its source inventory before returning. `bigram_snapshot_loads` and `secondary_snapshot_loads` in warm metrics distinguish a restored filter from a restored companion index. The companion contains typed postings, field-presence bits, ordered view keys, key summaries, and optional rendered full-text postings; a collection with no declared fields can use its saved bigram filter without loading that companion.

When a schema declares Markdown, HTML, XML, or `exclude_fts`, every included JSON leaf contributes to a separate index pair over rendered text and decoded source values. That pair is built alongside the normal index from the same source read and JSON parse. Other collections use the normal bigram index for standalone word and regex candidates, and `:fts` does not trigger a separate build. `warm_text_index` and `rebuild_text_index` act only on collections that need the pair. See [full-text.md](full-text.md) for field formats, matching modes, and source verification.

`build_posting(collection, path)` and `build_posting_all(path)` build or replace one runtime ordered posting for a JSON path. They read current source files, record scalar values plus separate null and missing keys, and retain path presence. The posting can answer `missing(path)`, `exists(path)`, safe scalar comparisons, and existential comparisons over complete repeated values. Ordinary scalar queries still report cardinality errors when a path yields multiple values. Full picker rebuilds rebuild runtime path postings after slot compaction. Source refresh marks them stale until explicitly rebuilt. `infer_and_auto_index` rescans JSON on request, reports nested field shapes and semantic hints, and builds postings for inferred booleans, numbers, and bounded low-cardinality strings. Saved root `x-index-paths` rules are loaded in one batched source pass after the normal picker build. See [inference.md](inference.md).

## Query reads

The default `auto` backend and explicit `bigram` backend select candidates through the picker. Safe typed comparisons and fields required by every matching branch narrow candidates; typed `OR` branches are unioned only when every branch has a safe indexed set. Selective bitsets enumerate set slots and sort those candidates by ID, including changed files; dense bitsets use the already sorted ID table. Covered top-level scalar equality, inequality, and range predicates and `exists` can get exact match sets directly from typed and presence indexes. Counted queries use the current index snapshot without checking every matching source file; only returned page records are read, parsed, and validated. This exact path falls back to source scanning for unsupported expressions, array-cardinality risk, or a changed-file overlay. `direct` evaluates source files without an index. `grep` uses ripgrep over source files as a candidate prefilter. These remain useful for parity checks and query shapes that need a broad scan.

`query_json_stream` emits validated page records through a callback in collection and ID order. Bounded candidate batches may run in parallel, then publish in order. The final summary confirms the total and metadata; a later error invalidates provisional records. The CLI's `--output events` writes the corresponding JSON lines.

View sorting uses ordered keys for explicitly indexed scalar fields, including bytewise string order. Null, missing, and invalid-type positions retain their view order. The older collection-view API still uses legacy UI settings; independent named views use native query arguments.

Schema validation runs for returned JSON query matches, in-memory view pages, and explicit validation commands only when a collection has a schema. A parseable `get_record` response remains `pending` until validated, or reports `no_schema` if no schema is attached. Schema-free views default to `@id`. No validation state or reference edge is stored in the index. Outgoing references are extracted from schema-declared paths in requested records; incoming references include previously observed edges unless complete coverage is requested, which scans referring source collections.

## Freshness

`metadata-on-open` builds or checks a collection on first use of a handle. `metadata-on-request` repeats source metadata checks. `hash-on-request` rebuilds the picker on each request. `refresh` explicitly reconciles one collection. Under an on-open policy, call `refresh` after an external edit to make it visible to index selection. A changed page file read before refresh can produce `Unstable` rather than a stale result. Query results are not cached; warm page requests still read selected source records.
