# Built-in source adapter and provider refresh control

The code input for this stage was `d61f99710831` on `library-extensions-stage2-wip`; the change is committed as `5be7861a9b29`. The normal release candidate was built from the working tree after the built-in filesystem JSON source was moved behind `SourceProvider` and provider-backed `refresh` was added. Only tests and documentation changed after that build. The candidate executable SHA-256 is `2a9464bd693e3cc1087982a25dd45918629d0bad6b18a88b7b05637dd8ad18ea`; its local executable is in the ignored `candidate-bin/` directory. The reference is the preserved `5b6-json-query-mix` from the previous stage; `json-50/manifest.json` records its path and hash.

`json-50/` contains the raw stdout, stderr, command, exit status and case summaries from `run_paired_json_extension.py`: 50 loaded Musenalm cases, seven query rounds per process, one warmup and three alternating pairs for each 0/64 MiB query-cache setting, ASCII bigrams, 16 Rayon threads and CPU affinity 0-15. The runner verified the pinned Musenalm source and metadata fingerprint before timing. Every reference/candidate count and first-ID signature matched, as did the recorded candidate scans, source reads and parses for all 50 cases. Median of per-case paired deltas was -0.043 ms with cache off and -0.023 ms with 64 MiB cache. The largest positive per-case median paired delta was +0.234 ms (case 13, cache off); cache-on maximum was +0.015 ms. The `summary.json` file retains all per-case samples and deltas. These are warm-filesystem results, not cold-storage results.

`cargo test --locked --workspace --all-targets` and `cargo clippy --locked --workspace --all-targets -- -D warnings` passed. The source adapter test verifies an actual nested locator, identical bytes and rejection of a changed revision. The external consumer tests exercise provider additions, renames and removals through explicit `refresh` under `MetadataOnOpen`. A deterministic mixed JSON/Markdown mutation sequence compares incremental results against a fresh repository after every edit, insert, rename and delete, checking complete ordered rows, counts, truncation, projected values and errors at both page and full-result limits. A new cache test checks that a collection refresh invalidates frontend scopes containing that collection. The repository spacing check still fails on preexisting workspace formatting differences; changed files were formatted and spaced individually.

This is a targeted stage control, not Gate 4 or final acceptance. Custom-format records are still absent from `FilePicker` postings and snapshots, and legacy JSON/text queries over a provider-backed collection still return an explicit unsupported error. The frontend still uses an exact scan and bounded heap sort on its first query. Large-corpus build/restore and complete-result comparisons have not been repeated for this stage.
