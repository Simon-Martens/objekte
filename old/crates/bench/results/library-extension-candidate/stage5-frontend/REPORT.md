# Registered frontend stage control

The effective final source is `c2e267a2f1`, tree-identical to `5b6217f3e5`. `61d0d66502` tried marking the new frontend path cold; the paired control found no benefit and `c2e267a2f1` reverted it. Earlier stage revisions were `0d3a63c292` (exact logical executor) and `398afa898d` (complete ordered-cache reuse). Reference revisions were `01a79d179f`, `eee23778d2`, and stage 3 `69be4383e9`. Raw directories contain every command, exit status, stderr, stdout, binary SHA-256, seven-sample case rows, and paired summaries. The input fingerprint was checked against `crates/bench/results/library-extension-baseline/266d9a0fb071-20261104T113205Z/corpora.json` before each JSON run. Binaries in `candidate-bin/` are preserved locally and ignored by Git.

The normal release `json-50-final/` control compared `398afa898d` with `eee23778d2`: 50 loaded Musenalm cases, ASCII bigrams, cache budgets 0 and 64 MiB, seven rounds, three alternating pairs, 16 Rayon threads and CPU affinity 0-15. Every recorded count/first-ID signature and scan/read/parse count matched. Median of per-case paired deltas was +0.002 ms at cache 0 and -0.043 ms at cache 64. Four cache-off cases had median paired deltas above +0.5 ms, at most +0.994 ms, with order-dependent spread; no cache-on case exceeded +0.053 ms.

The `json-50-final-followup/` control compared the effective final `5b6217f3e5` tree with `398afa898d` under the same protocol. Signatures and source work again matched. Median of per-case paired deltas was +0.071 ms at cache 0 and +0.063 ms at cache 64. Cases 40 and 45 were consistently about +0.8 to +1.2 ms in both cache modes; case 41 was about +0.7 to +0.9 ms at cache 64. This is a small, repeatable slowdown in those cases, recorded rather than hidden. The user's later instruction permits small absolute differences while rejecting roughly 80–100 ms gaps. It does not establish universal zero overhead or complete performance acceptance.

The earlier `json-50-control/` and `json-suspects/` runs compared `0d3a63c292` with `01a79d179f`. The isolated `json-suspects-01a-to-eee/` and `json-suspects-eee-to-0d3/` runs show that most of the roughly 1 ms difference in original cases 25, 40, 41 and 45 was already present by `eee23778d2`; the frontend code added roughly 0.2–0.3 ms in cases 40/41 in that comparison. The `json-suspects-cold/` trial compared the later cold annotation with `5b6217f3e5`; all median paired deltas were close to zero, so that annotation was reverted. A failed full worktree checkout attempted to copy hundreds of thousands of tracked corpus files into `/tmp` and exhausted temporary storage; Git removed the incomplete checkout. The exact `eee23778d2` executable was instead rebuilt from a source-only archive; its SHA-256 matched the already preserved executable used in the prior stage.

The normal release Musenalm FTS4 build controls used one warmup and five alternating reference/candidate pairs, 16 Rayon threads, affinity 0-15, no allocator or stage timers, and no snapshot. `index-build-fts4-final/` compared `398afa898d` with `69be4383e9`: medians 1590.1 versus 1594.3 ms (+0.3%). `index-build-fts4-effective-final/` compared the effective final tree with `69be4383e9`: medians 1585.0 versus 1595.8 ms (+0.7%). One candidate sample was 1701.0 ms, about 96 ms slower than its pair. Because of that outlier, `index-build-fts4-effective-final-repeat/` ran another five pairs: medians 1582.5 versus 1591.4 ms (+0.6%), without another 80–100 ms gap. All controls built 133,948 records with equal compressed index sizes. These are warm-filesystem, index-cache-free build controls, not cold physical-storage measurements.

Workspace tests and Clippy passed at the effective final tree. The final workspace test used `CARGO_BUILD_JOBS=2` after an unbounded parallel rebuild saturated memory with concurrent linkers; that earlier attempt was interrupted before tests ran. The external consumer crate has 18 passing tests, including mixed JSON/Markdown frontend queries, Boolean composition, year extraction and sort ties, cached page reads, request freshness, initial empty provider selection, schema reload, array markup binding, and registration-order-independent identity. The `index-timings` plus `allocation-profile` bench feature test build passed. The repository-wide spacing check still fails on the same four preexisting files (`bigram/filter.rs`, `config/discovery.rs`, `repository/text_query/sorted.rs`, `tests/index_build_profile.rs`); changed Rust files were formatted and spaced individually.

Gate 4 and Gate 5 remain open. Provider-backed records are queryable through the new exact frontend path, but they are not in the JSON-only `FilePicker`, its bigram/typed postings, legacy query execution, refresh path, or index snapshots. The full Phase 0 corpus/workload matrix, complete large-result signatures, source-mutation timings, and snapshot restoration profiles have not been repeated against this tree. None of these stage controls proves final performance acceptance.
