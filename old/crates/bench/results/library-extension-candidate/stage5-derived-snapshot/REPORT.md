# Selected derived snapshot stage control

## Inputs and commands

Starting revision: `502e2eb460` on `library-extensions-stage2-wip`; implementation commit: `f3f7bc45b7`. This stage adds an opt-in versioned, checksummed snapshot for the selected-provider typed posting. `manifest.json` records the release binary hashes, toolchain, host target, fixture and raw output checksums. Executables are preserved under ignored `candidate-bin/`, outside the commit.

Five independent normal-release processes ran `RAYON_NUM_THREADS=16 taskset -c 0-15 candidate-bin/frontend_derived_compare 7 sort`. Each generated 20,000 JSON and 100 Markdown sources before timing. The same filename/content SHA-256 `436463c8fb0fef71587b186d716b658c3955e48388f9f13daf7ae96c2dde88bd` appeared in all five runs. Within each process, scan, indexed, saved and restored paths used the same source paths and metadata. The example measured derived build, snapshot save and restore separately, verified complete ordered IDs, count and truncation, and recorded every query sample. Output files are `frontend-sorted.json` and `frontend-sorted-02.json` through `frontend-sorted-05.json`. Restore timing excludes opening the repository; it includes enumerating current provider sources and checksum validation. These are warm filesystem-cache results.

The normal JSON control used `run_paired_json_extension.py` against the preserved prior-stage and candidate release binaries, the same pinned Musenalm paths and metadata, 50-case workload SHA-256 `d7e6967dc1250cf28c054027c72fba8452f5ccd4e8fe3eea9653423fa135e7d7`, ASCII encoding, 16 Rayon threads and CPU affinity 0–15. It ran three alternating process pairs and seven measured rounds per process at both 0 and 64 MiB query-cache budgets. Its exact commands, exits, per-case samples and checks are under `json-50/`. Case 45 was repeated in isolation with five alternating pairs and 15 rounds at each budget; `case45-paired/` has the raw output and `case45-workload.json` preserves the exact filter with sequential case ID.

## Results

The 63,637-byte selected typed snapshot restored in a median 65.121 ms (65.073–66.438 ms) across five processes, with zero source reads and parses. Fresh derived posting build took median 143.483 ms (143.395–145.768 ms). Snapshot save took median 66.026 ms (65.307–66.372 ms). Restore still scans current source metadata to validate revisions, so these are distinct operations, not equal-work timing. All five restored complete 200-ID orders, counts and truncation flags matched the scan. The seven measured indexed query rounds in each process retained the prior stage's approximately 1.7 ms median and 201 source reads versus about 135 ms and 20,101 reads for the scan; every sample is retained.

All 50 default JSON case signatures and per-case scans, reads and parses matched for both budgets in every pair. The median case delta (candidate minus previous stage) was +0.016 ms at cache 0 and +0.016 ms at cache 64. The largest positive median of paired medians was case 45 (`owner = 'Theodor Springmann Stiftung' && basis = true`): +0.739 ms at cache 0 and +0.664 ms at cache 64 against roughly 31.5 ms reference medians. The isolated repeat confirmed a small difference with unchanged work: cache 0 paired deltas +0.824, +0.644, +0.696, +0.689 and +0.656 ms (median +0.689 ms); cache 64 deltas +0.807, +0.668, +0.612, +0.669 and +0.619 ms (median +0.668 ms). This is a reproducible approximately 2.1–2.2% timing difference, below the user's stated material absolute slowdown examples, and its cause is unresolved. It is recorded as a case-specific observation, not a general overhead allowance. `json-50/summary.json` lists every per-case delta.

An exploratory stricter trailing-payload check was then added to restore decoding. Its release binary produced a larger repeatable case-45 slowdown of +1.638 ms at cache 0 and +1.647 ms at cache 64, with equal work counts. The five `frontend-final-*.json` outputs and `json-50-final/` preserve that rejected attempt. The extra check was reverted before committing production code. The retained snapshot validates magic, exact file length, checksum, bounded decoding and semantic/source identities.

## Correctness and limits

The external consumer test checks a successful restore with no source reads or parses, exact sorted results, checksum corruption, changed extractor semantic version, and changed source revision. The posting is inserted only after complete validation. `cargo test --locked --workspace --all-targets -q`, `cargo clippy --locked --workspace --all-targets -- -D warnings`, and `cargo test --locked -p objekte-bench --features index-timings,allocation-profile --all-targets -q` passed. Changed Rust files pass rustfmt and `git diff --check`. The whole-workspace spacing check still finds the same seven pre-existing hunks in five untouched files; its output is saved here.

The selected derived snapshot is an explicit API; automatic cache persistence, representation-posting persistence, legacy query inclusion of provider sources, and the complete Phase 0 performance matrix remain open. This stage does not establish final acceptance.
